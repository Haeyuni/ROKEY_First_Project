# 예외처리 가이드 v0.1

현재 코드 기준 예외처리 동작 정리. **핵심 전제**: 안착 센서·더스트 컬렉터·F/T
센서가 전부 하드웨어에 없거나 작동하지 않아, 힘/센서 기반 예외처리는 실제로는
대부분 꺼져 있고 **좌표(티칭값) 기반 이동 + 안전/취소/타임아웃 감시**만 실동작한다.
NIS v0.3 문서(§7)는 이 상태를 반영하지 못해 최신이 아니다.

## 1. 실제로 동작하는 예외처리 (센서 무관)

| 코드 | 발생 조건 | severity |
|---|---|---|
| `E_INVALID_GOAL` | goal 필드 누락/범위 오류 | ABORT |
| `E_SAFETY_BLOCKED` | `safe_to_move=false` | SAFETY |
| `E_PRECOND_FAILED` | ValidatePrecondition 실패 | ABORT |
| `E_TIMEOUT` | 동작/응답 대기 시간 초과 | ABORT |
| `E_CANCELLED` | 사용자 취소 | NONE |
| `E_COMM_LOST` | 하위 액션 서버 연결 실패 | ABORT |
| `E_MOTION_FAILED` | TF 변환 실패, NOT REACHABLE(도착 오차 초과) | ABORT |
| `E_GRIP_FAILED` | 그리퍼 명령 실패 | RETRY |
| `E_TOOL_DROP` | `/tool/status.grip_verified=false` & 툴 보유 중 | SAFETY |

이 코드들은 F/T 센서 여부와 무관하게 항상 감시된다 — 실제 운용에서 발생하는
예외는 거의 이 목록 안에서 나온다.

## 2. 힘/센서 기반 예외처리 — 현재 비활성

| 코드 | 원래 의도 | 현재 상태 |
|---|---|---|
| `E_NO_CONTACT` | 접촉 탐색 깊이 내 미검출 | 미발생 — 좌표까지 직접 이동, 접촉 탐색 자체를 안 함 |
| `E_OVERFORCE` | 힘 상한 초과 | 미발생 — 힘 감시 안 함 |
| `E_LOW_STIFFNESS` | 강성 하한 미만(피부 접촉 의심) | 미발생 — 강성 측정 자체를 안 함 |
| `E_LATERAL_LIMIT` | 수평 접근 진행 한계 초과 | 미발생 — travel_limit까지 그냥 전진 |
| `E_LATERAL_JAM` | 진행축 저항 급증(걸림 의심) | 미발생 — 저항 감시 안 함 |

`robot_skill_node`의 `contact_force_sensing_enabled`(ContactPath),
`lateral_force_sensing_enabled`(LateralContact) 파라미터 **기본값 자체가
`False`다** — F/T 센서가 힘을 아예 인식하지 못하는 것이 실기에서 재확인돼
(2026-08-24) 두 파라미터의 코드 기본값을 `True→False`로 전환했다
(`robot_skill_node.py:207,221`). 이전엔 `True`로 두면 `E_LATERAL_LIMIT`
등이 항상 발생해 공정을 완료할 수 없었다.

`False`일 때 실제로 하는 일:
- 접촉 탐색(힘 임계값 도달까지 하강/전진) 생략 → waypoint 좌표(티칭값)를
  "이미 표면/한계"로 신뢰하고 그대로 이동
- 컴플라이언스·목표힘 추종(`compliance_on`/`set_desired_force`) 생략
- 과압·걸림·강성 감시 전부 생략
- 취소 요청, `safe_to_move`, 타임아웃 감시는 그대로 유지 (안전 계층 자체는 우회 아님)

**즉 좌표 티칭이 정확한지가 유일한 안전장치다** — waypoint의 z, `travel_limit_mm`이
실제로 안전한 값인지는 사람이 보장해야 한다. `sanding_node`가 이 제약에
가장 먼저 부딪혀, 압입 깊이를 컴플라이언스 대신 `engagement_depth_mm`
파라미터(기본 2.0mm)로 waypoint 좌표 자체를 밀어 넣는 방식으로 바꿨다 —
이 값이 `travel_limit_mm`(경계까지 거리 − 안전 마진)을 넘으면 REJECT된다.

## 3. 안전 결함 (`SafetyState`, safety_monitor)

| 코드 | 트리거 | 해제 |
|---|---|---|
| `FAULT_ESTOP` | `robot_state ∈ {6,7}` 진입 | 물리 해제 + `ResetSafety(confirm=true)` |
| `FAULT_COMM_LOST` | `get_robot_state()` 폴링 실패/타임아웃 | 통신 복구 + `ResetSafety` |
| `FAULT_TOOL_DROP` | `/tool/status.grip_verified=false` & 툴 보유 중 | 사람 확인 + `ResetSafety` |

- 세 결함 모두 물리 원인이 사라져도 **자동 해제 안 됨**.
- 그리퍼 폭 되읽기 센서가 없어 `tool_manager`가 항상 `grip_verified=True`로
  발행 → `FAULT_TOOL_DROP`은 이 경로로는 실질적으로 발생하지 않음.
- `_estop_pressed` 초기값은 `True`(fail-safe).

## 4. tool_manager 예외처리

- 파지 폭 실측 불가(센서 없음) → `PickPlace` 성공/실패만으로 파지 판단.
- 파지 실패/불확실 시 `_mark_tool_lost()`로 `current_tool=NONE` 확정 발행.
- 랙 이동 전 `NEUTRAL_TCP` 전환 실패 → `ChangeTool` 자체 abort.
- 현재 툴 반납 실패 시 "여전히 쥔 채"임을 그대로 발행 후 abort.

## 5. session_orchestrator ABORT 뒷정리 순서

1. 툴 보유 중이면 반납 시도(취소 요청 무시하고 강제 실행).
2. 반납 실패 + **UV 보유 중** → HOME 복귀 생략, 현재 위치 정지, 수동 개입 요청 로그.
3. 그 외 툴 반납 실패 → HOME은 시도하되 수동 확인 요청 로그.
4. `abort_return_home=true`면 HOME 복귀.

재작업(REWORK) 루프 없음 — scan/inspection 노드 폐지로 경화 부족 판정 근거가
사라져 사람이 육안 판단.

## 6. 하드웨어 미장착·미작동 대응 정리

| 항목 | 상태 | 제거/비활성된 것 | 대체 수단 |
|---|---|---|---|
| 안착 센서 | 미장착 | precheck 안착 확인, `FAULT_NO_HANDREST` (코드에서 완전 삭제) | 육안 확인 |
| 더스트 컬렉터 | 미장착 | `FAULT_NO_DUST`, DI 폴링, `SandSurface` 사전조건 (코드에서 완전 삭제) | 육안 확인 |
| F/T 센서 | 미작동 | 접촉 탐색·힘 추종·과압/걸림/저강성 감시 (파라미터로 비활성화, 코드는 남아있음) | 좌표 티칭값을 표면/한계로 신뢰 |

세 항목 모두 장비가 정상화되면 되살려야 한다. 안착 센서·더스트 컬렉터는 코드
자체가 삭제돼 복원하려면 git 이력(`d9b9960`, `2f0287e`)에서 되돌려야 하고,
F/T 센서는 코드가 남아 있으니 `*_force_sensing_enabled`를 `True`로 되돌리기만
하면 된다.

## 7. safety_monitor 하트비트 파라미터 (현재값)

`publish_rate_hz=3`, `heartbeat_timeout_ms=3000` — `ChangeTool`(PickPlace) 이동 중
서비스 호출이 몰려 `FAULT_COMM_LOST` 오탐이 반복 재발해 낮춘 값.
`safety_monitor_node.py` 기본값과 `test_bringup.launch.py` launch 인자 기본값을
함께 맞춰야 실제로 반영됨.

발행 주기를 낮추면서 소비 노드 쪽 타임아웃도 맞춰야 했다: `safety_status_timeout_s`가
8개 노드에서 `0.2s`로 남아있으면 발행 간격(≈333ms)보다 짧아 정상 수신 중에도
주기적으로 `safe_to_move=false`로 오판(`E_SAFETY_BLOCKED`)한다 — 발행 간격 대비
3배 여유를 두고 전 노드 `1.0s`로 통일했다.
