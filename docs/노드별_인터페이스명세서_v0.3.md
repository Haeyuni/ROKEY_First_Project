## 1. 읽는 법

각 노드는 아래 **8개 항목**으로 동일하게 기술됩니다.

| 항목 | 뜻 |
|---|---|
| **역할** | 이 노드가 존재하는 이유 한 줄 |
| **제공 (서버)** | 다른 노드가 이 노드를 호출할 때 쓰는 인터페이스 |
| **소비 (클라이언트)** | 이 노드가 다른 노드를 호출할 때 쓰는 인터페이스 |
| **파라미터** | `declare_parameter`로 선언할 설정값 ← **v0.2 신설** |
| **동작** | 요청을 받고 나서 하는 일의 순서 |
| **반환값** | result 필드 각각의 의미와, 호출자가 그걸로 뭘 판단하는지 |
| **피드백** | 실행 중 흘려보내는 정보와 주기 |
| **주요 에러** | 실패 코드, 원인, 처리 방식 |

### 표기 규칙

| 표기 | 뜻 |
|---|---|
| `Action` | 오래 걸리고 취소 가능. goal → feedback → result |
| `Service` | 즉답 (목표 응답 5 ms 이내). 블로킹 호출 금지, 반드시 async |
| `Topic(pub)` | 이 노드가 발행 |
| `Topic(sub)` | 이 노드가 구독 |
| `TF` | 좌표 변환 브로드캐스트/조회 |
| ★ | 실패 시 프로젝트 전체가 막히는 지점 |

파라미터 표의 **`캘`** 표시는 실측 캘리브레이션으로 확정해야 하는 값입니다. 착수 시점에는 표의 값을 임시로 쓰되, C-01/C-02 실험 결과로 반드시 덮어씁니다.

> **⚠️ 서비스 호출 주의**
> ROS2에서 콜백 안에서 서비스를 동기 호출하면 **데드락**이 납니다. 액션 서버의 `goal_callback` 안에서 `ValidatePrecondition`을 부르는 코드가 전 노드에 반복해서 나오므로, **반드시 `MutuallyExclusiveCallbackGroup`을 분리하거나 async 호출**을 쓰세요. 이 프로젝트에서 가장 나오기 쉬운 버그입니다.

## 3. 모든 노드가 지켜야 할 공통 규약

**이 장의 규약을 어기는 코드는 리뷰에서 반려합니다.** 12개 노드가 제각각 동작하면 통합이 불가능해집니다.

### 3.1 액션 서버 표준 수명주기

```
① goal 수신
      ↓
② 파라미터 유효성 검사        → 실패 시 REJECT (E_INVALID_GOAL)
      ↓
③ /safety/status.safe_to_move 확인 → false면 REJECT (E_SAFETY_BLOCKED)
      ↓
④ ValidatePrecondition 호출   → ok=false면 REJECT (E_PRECOND_FAILED)
      ↓
⑤ ACCEPT → 실행 시작
      ↓
⑥ 실행 중 매 주기:
      · feedback 발행
      · is_cancel_requested 확인   → true면 안전 정지 → CANCELED
      · safe_to_move 재확인        → false면 즉시 정지 → ABORT
      ↓
⑦ 종료 처리 (성공/실패/취소 공통):
      · 툴을 표면에서 이탈시킨다
      · 필요 시 HOME 복귀
      · result 채워서 반환
```

> **③④를 goal 수락 전에 하는 이유**: 이미 수락한 goal을 도중에 죽이는 것보다, 애초에 받지 않는 편이 로봇이 움직이지 않아 안전하고 로그도 깔끔합니다.

### 3.2 REJECT vs ABORT 구분

| | 언제 | 로봇 상태 |
|---|---|---|
| **REJECT** | goal을 **받기 전** 판단. 전제조건 미충족 | **한 번도 안 움직임** |
| **ABORT** | goal을 받고 **실행 중** 실패 | 움직이던 중 정지 → 이탈 → HOME |
| **CANCEL** | 외부에서 취소 요청 | 정지 → 이탈 → HOME |

`ABORT`와 `CANCEL`은 뒷정리(이탈 + HOME)가 **완전히 같습니다.** 공통 함수 하나로 구현하세요.

**단, 이탈 방향은 접근 방향에 따라 다릅니다.** `ContactPath`는 표면 법선 이탈, `LateralContact`는 접근 벡터 역방향 이탈입니다. §5.1 참조.

### 3.3 취소 전파 규칙

```
RunSession cancel
   → 진행 중인 공정 액션(예: SandSurface) cancel
      → 진행 중인 스킬 액션(LateralContact) cancel
         → dsr 정지 명령
```

**공정 노드는 자기가 호출한 스킬 액션의 goal_handle을 반드시 멤버로 보관**해야 합니다.

### 3.4 안전 상태 구독 의무

**모든 노드는 `/safety/status`를 구독합니다.** 예외 없습니다. `safe_to_move == false`가 관측되면:

- 액션 서버는 실행 중인 goal을 `ABORT(E_SAFETY_BLOCKED)`
- 새 goal은 `REJECT`
- `curing_node`는 추가로 **즉시 조사 영역 밖으로 이탈** (v0.2: permit 반납이 아니라 물리적 회피)

### 3.5 로깅 규칙

| 레벨 | 쓰는 경우 |
|---|---|
| `DEBUG` | 매 주기 힘 값 등 대량 데이터 |
| `INFO` | goal 수락/완료, 상태 전이 |
| `WARN` | 재시도, 임계값 근접 |
| `ERROR` | ABORT, 통신 실패, 안전 결함 |

모든 ABORT 로그는 **에러 코드 문자열을 반드시 포함**합니다: `[E_LOW_STIFFNESS] sanding aborted at (12.3, 4.5)`

### 3.6 파라미터 선언

모든 노드는 시작 시 `declare_parameter`로 설정을 선언하고, 하드코딩 상수를 두지 않습니다.

```python
self.declare_parameter('max_force_n', 5.0)
self.declare_parameter('use_mock_hardware', False)
```

**전 노드 공통 파라미터 (예외 없음)**

| 이름 | 타입 | 기본 | 설명 |
|---|---|---|---|
| `use_mock_hardware` | bool | `false` | Phase 0 mock 개발 전제 |
| `node_timeout_s` | double | `120.0` | 액션 자체 타임아웃 |
| `safety_topic` | string | `/safety/status` | 안전 토픽 경로 |
| `log_force_data` | bool | `false` | DEBUG 힘 로그 on/off |

파라미터 파일은 `config/<node_name>.yaml` 하나씩 두고, launch에서 주입합니다. **런치 인자 하나(`use_mock_hardware:=true`)로 전 노드가 mock으로 전환**되어야 합니다.

## 4. 공통 에러 코드

`result.error` 필드에 아래 문자열을 그대로 넣습니다. 자유 서술 금지 — 웹에서 파싱해 사용자 메시지로 바꿔야 합니다.

| 코드 | 의미 | 주 발생 노드 | 결과 |
|---|---|---|---|
| `E_INVALID_GOAL` | 파라미터 범위 위반 | 전체 | REJECT |
| `E_SAFETY_BLOCKED` | `safe_to_move == false` | 전체 | REJECT / ABORT |
| `E_PRECOND_FAILED` | 전제조건 검사 실패 | 공정 노드 | REJECT |
| `E_TOOL_MISMATCH` | 요구 툴 ≠ 장착 툴 | 공정 노드 | REJECT |
| `E_GRIP_FAILED` | 파지 폭 검증 실패 | robot_skill, tool_manager | ABORT |
| `E_TOOL_DROP` | 이동 중 파지 상실 | robot_skill | ABORT + 안전 정지 |
| `E_NO_CONTACT` | 탐색 깊이 내 표면 미검출 | robot_skill (ContactPath) | ABORT |
| `E_OVERFORCE` | `max_force_n` 초과 | robot_skill | ABORT + 즉시 후퇴 |
| `E_LOW_STIFFNESS` ★ | 강성 하한 미만 = **피부 접촉 의심** | robot_skill | ABORT + 즉시 후퇴 |
| **`E_LATERAL_LIMIT`** ★ | 수평 이동 한계 초과 = **손가락 방향 진행** | robot_skill (Lateral) | ABORT + 즉시 후퇴 |
| **`E_LATERAL_JAM`** | 수평 저항 급증 = 모서리 걸림 | robot_skill (Lateral) | ABORT + 후퇴 |
| `E_MOTION_FAILED` | 드라이버 실패 (특이점·한계·서비스 오류) | robot_skill | ABORT |
| `E_COMM_LOST` | 하트비트 타임아웃 | safety_monitor | 전체 ABORT |
| `E_TIMEOUT` | 액션 자체 타임아웃 | 전체 | ABORT |
| `E_CANCELLED` | 사용자/상위 취소 | 전체 | CANCELED |

**v0.3에서 삭제된 코드** (스캔·검사·재작업 폐지):
`E_NO_SCAN`, `E_SEPARATION_LOW`, `E_COARSE_INSUFFICIENT`, `E_MAP_SESSION_MISMATCH`,
`E_REWORK_EXCEEDED`, `E_STONE_MISS`

**v0.2에서 삭제된 코드**: `E_UV_DENIED`, `E_UV_TIMEOUT` (permit 폐지)

> **★ 두 개가 이 프로젝트의 성패를 가릅니다.**
> `E_LOW_STIFFNESS`와 `E_LATERAL_LIMIT`은 **피부를 갈 뻔했다**는 뜻입니다.
> 이 둘은 **로그에 반드시 좌표와 측정값을 함께 남기세요.**
>
> ⚠️ v0.3 에서 이 방어선이 **한 겹 얇아졌습니다.** 예전에는 스캔이 "여기는
> 손톱, 여기는 피부"를 측정으로 갈라줬고 그게 틀리면 `E_SEPARATION_LOW` 로
> 공정 자체가 시작되지 않았습니다. 지금은 그 구분이 사람이 티칭한
> `nail_local_frame` + `nail_region` 값 하나뿐이고, **그 값이 틀렸는지
> 알려주는 코드는 없습니다.** §6.0 참조.

#### 동작

**`MoveTo`**
```
1. target을 base_0 기준으로 TF 변환
2. linear=true면 movel, false면 movej 호출
3. 완료 대기 (드라이버 응답 + 자세 오차 확인)
```

**`PickPlace`** — P01~P13을 전부 대체
```
PICK :  targets.yaml에서 target_key 조회
        → 접근 높이로 이동 → 하강 → 그리퍼 Close
        → verify_grip이면 폭 피드백 확인 → 상승
PLACE:  접근 높이로 이동 → 하강 → 그리퍼 Open → 상승
```

**`ContactPath`** — M02/M03 (브러싱·도포)
```
1. 시작점 위 접근 높이로 이동
2. 표면 탐색: contact_search_speed_mms로 하강하며 접촉 감지
   → contact_search_max_depth_mm 내 미검출이면 E_NO_CONTACT
3. target_force까지 천천히 접촉
4. use_compliance면 순응제어 활성화
5. waypoints 순회. 매 주기(20 Hz):
     · |F| > max_force_n            → +Z 후퇴 + E_OVERFORCE
     · k < min_stiffness (옵션 on)  → +Z 후퇴 + E_LOW_STIFFNESS
     · 취소/안전 확인
6. 순응제어 해제 → +Z 이탈
```

**`LateralContact`** ← **v0.2 신설, M01 전용**
```
0. goal 필수 필드
     approach_vector   : nail_local_frame 기준 접근 방향 단위벡터 (수평)
     work_plane_z_mm   : 작업 평면 높이 (표면에서 띄울 값)
     waypoints         : 접근 벡터에 수직인 평면 내 경로
     target_force_n    : 접근 벡터 방향으로 유지할 접촉력
     travel_limit_mm   : 접근 벡터 방향 최대 진행 거리 ★

1. 안전 대기점 → work_plane_z_mm 높이로 수평 이동
2. 수평 탐색: approach_vector 방향으로 lateral_search_speed_mms 전진
     · 접촉 감지 = approach_vector 성분 힘 > lateral_contact_threshold_n
     · travel_limit_mm 초과해도 미접촉 → 즉시 후퇴 + E_LATERAL_LIMIT ★
3. target_force_n까지 전진
4. 순응제어: approach_vector 축만 힘 제어, 나머지는 위치 제어
5. waypoints 순회 (접근축에 수직인 평면 내 이동). 매 주기(20 Hz):
     · 접근축 힘 > max_force_n           → 후퇴 + E_OVERFORCE
     · 접근축 누적 진행 > travel_limit_mm → 후퇴 + E_LATERAL_LIMIT ★
     · 진행축 저항 > lateral_jam_force_n → 후퇴 + E_LATERAL_JAM
     · 취소/안전 확인
6. 순응제어 해제 → approach_vector 역방향으로 lateral_retreat_mm 후퇴
```

> **구현 참고 (2026-08-24)**: `contact_force_sensing_enabled`/
> `lateral_force_sensing_enabled`가 둘 다 기본값 `false`로 바뀌어, 위
> 동작 설명 중 "표면 탐색"·"target_force까지 접촉"·"순응제어"·힘/저항
> 기반 abort 단계(`E_NO_CONTACT`/`E_OVERFORCE`/`E_LOW_STIFFNESS`/
> `E_LATERAL_LIMIT`/`E_LATERAL_JAM`)는 **현재 실행되지 않습니다.**
> waypoints 좌표(티칭값)를 그대로 따라가며, 취소/안전/타임아웃 감시만
> 유지됩니다. 좌표가 실제로 안전한지는 사람이 보장해야 합니다 — 자세한
> 내용은 `docs/예외처리_가이드_v0.1.md` 참고.

> **⚠️ `ContactPath`와 `LateralContact`를 하나로 합치지 마세요.**
> 겉보기엔 "힘 유지하며 경로 추종"으로 같아 보이지만, 안전 감시 논리가 다릅니다.
>
> - **법선 접근(`ContactPath`)**: 압입 강성 `ΔF/Δz`를 계속 측정할 수 있어, 강성이 떨어지면 "피부에 닿았다"고 판정 가능
> - **수평 접근(`LateralContact`)**: 접근축으로 밀고 있을 뿐 압입이 아니므로 **강성을 못 잽니다.** `E_LOW_STIFFNESS`가 작동하지 않습니다
>
> 따라서 수평 연마에서 피부 접촉을 막는 유일한 수단은 **`travel_limit_mm`(기하학적 한계)**입니다. 이 값은 손톱 경계에서 계산한 "경계까지의 거리 − 안전 마진"이어야 하며, 넉넉하게 잡으면 안전장치가 아니라 장식이 됩니다.
>
> ⚠️ **v0.3**: 그 "경계"가 이제 측정값이 아니라 티칭값입니다(§6.0). 계산식은
> 그대로지만 입력의 성격이 달라졌습니다.

> **v0.3 폐지: `ProbePoint`(`/skill/probe_point`)**
> 한 점을 압입해 강성·이탈력을 재던 스킬입니다. 소비자가 `scan_node`(경계
> 판별) · `inspection_node`(경화 판정) · `stone_node`(부착 검증) 셋뿐이었고
> 전부 폐지·축소되면서 함께 삭제됐습니다. 이 노드에서 힘 기반 표면 탐색이
> 필요하면 `ContactPath` 를 쓰세요 — 다만 `ContactPath` 는 접촉 깊이를
> 돌려주지 않고 끝나면 항상 후퇴합니다. 압입 깊이를 알아야 하는 동작은
> 지금 이 워크스페이스에 없습니다(`stone_node` 는 티칭된 높이를 씁니다).

#### 반환값

| 액션 | 필드 | 호출자가 이걸로 판단하는 것 |
|---|---|---|
| `MoveTo` | `final_pose` | 목표 대비 오차가 허용범위인가 |
| `PickPlace` | `measured_width` | 파지 성공 여부 |
| `ContactPath` | `mean_force` / `max_force` | 힘 제어가 잘 됐는가 |
| `ContactPath` | `path_error` | 경로 이탈 정도 |
| `ContactPath` | `abort_reason` | `ABORT_LOW_STIFFNESS`면 피부 접촉 시도 |
| **`LateralContact`** | `mean_force` / `max_force` | 접근축 힘 유지 품질 (M01 성공 기준) |
| **`LateralContact`** | `max_travel_mm` | **접근축 최대 진행 거리. 한계 대비 여유 확인** |
| **`LateralContact`** | `max_jam_force_n` | 진행축 최대 저항 — 모서리 걸림 정도 |
| **`LateralContact`** | `abort_reason` | `ABORT_LATERAL_LIMIT`면 **경계 초과 진행 시도** |

> **판정은 이 노드가 하지 않습니다.** 이 노드는 힘·거리 숫자만 돌려주고,
> "여기까지가 손톱이다"라는 판단은 v0.3 부터 아예 런타임에 하지 않습니다 —
> `static_frames.yaml` 에 티칭된 값이 그 판단을 대신합니다(§6.0).

#### 피드백

| 액션 | 내용 | 주기 |
|---|---|---|
| `MoveTo` | `progress` | 10 Hz |
| `PickPlace` | `step`(0~4), `progress` | 단계 전환 시 |
| `ContactPath` | `progress`, `current_wrench` | 20 Hz |
| **`LateralContact`** | `progress`, `current_wrench`, **`travel_mm`** | 20 Hz |

`LateralContact`의 `travel_mm`은 웹에 **한계 대비 게이지**로 표시하세요. 연마 중 이 값이 한계에 붙어가는 게 보이면 실기 전에 궤적을 고칠 수 있습니다.

#### 주요 에러

| 코드 | 원인 | 처리 |
|---|---|---|
| `E_NO_CONTACT` | 탐색 깊이 내 표면 없음 | 상승 후 ABORT. 지그 안착 위치 의심 |
| `E_OVERFORCE` | 힘 상한 초과 | 즉시 후퇴 후 ABORT (법선=+Z, 수평=역벡터) |
| `E_LOW_STIFFNESS` | 피부 접촉 의심 | 즉시 +Z 후퇴 + 좌표 로그 후 ABORT |
| `E_LATERAL_LIMIT` ★ | 접근축 진행 한계 초과 | **즉시 역방향 후퇴** + 좌표 로그 후 ABORT |
| `E_LATERAL_JAM` | 진행축 저항 급증 | 후퇴 후 ABORT. 접근각·경로 재검토 |
| `E_GRIP_FAILED` | 폭 피드백 불일치 | 그리퍼 Open → 후퇴 → ABORT |
| `E_TOOL_DROP` | 이동 중 폭 변화 | **즉시 정지** |
| `E_MOTION_FAILED` | dsr 서비스 실패/특이점 | 정지 후 ABORT + 원본 에러 로그 |

### 5.2 `tool_manager`

> **역할**: 툴 랙 위치와 TCP 오프셋을 관리하고, 툴 교체를 원자적으로 수행한다.
> **담당**: 주은

#### 제공

| 인터페이스 | 통신 | 타입 |
|---|---|---|
| `/tool/change` | Action | `ChangeTool` |
| `/tool/get_info` | Service | `GetToolInfo` |
| `/tool/status` | Topic(pub) | `ToolState` (변경 시, TRANSIENT_LOCAL) |

#### 소비

`/skill/pick_place` (Action) · dsr TCP 설정 서비스 · `/safety/status`

#### 파라미터

| 이름 | 타입 | 기본 | 단위 | 설명 |
|---|---|---|---|---|
| `tool_list` | string[] | `[sander, brush, coater, uv, tweezers]` | — | 관리 대상 툴 (v0.3: `probe` 제거) |
| `rack_config_file` | string | `config/tool_rack.yaml` | — | 슬롯 좌표·TCP 오프셋 정의 |
| `approach_height_mm` | double | `50.0` | mm | 랙 접근 높이 |
| `verify_grip` | bool | `true` | — | 파지 후 폭 검증 |
| `grip_width_tolerance_mm` | double | `1.0` | mm | 폭 허용 오차 |
| `change_timeout_s` | double | `60.0` | s | 교체 전체 타임아웃 |
| `uv_park_facing` | string | `into_rack` | — | **UV 상시 ON이므로 반납 시 광축 방향 지정** (§7.0) |

`rack_config.yaml` 예시:
```yaml
tools:
  sander:
    slot_frame: slot_2
    expected_grip_width_mm: 18.0
    tcp_offset: [0, 0, 92.5, 0, 0, 0]
  uv:
    slot_frame: slot_5
    expected_grip_width_mm: 22.0
    tcp_offset: [0, 0, 110.0, 0, 0, 0]
```

#### 동작

```
1. 현재 툴이 있으면 → 랙 슬롯으로 PickPlace(PLACE)
     (uv 반납 시 uv_park_facing 자세로 배치)
2. 대상 툴 슬롯으로 이동 → PickPlace(PICK, verify_grip=true)
3. dsr에 해당 툴 TCP 오프셋 설정
4. 파지 폭 재확인 → /tool/status 발행
```

**툴 목록 (5종)**: `sander` · `brush` · `coater` · `uv` · `tweezers`

> **v0.3 삭제**: `probe`(탐침). `ProbePoint` 스킬과 그걸 쓰던 두 노드가
> 폐지돼 집을 일이 없습니다 — `tool_rack.yaml` 의 항목, `targets.yaml` 의
> `probe`/`probe_work` 좌표, `ToolState.PROBE` 상수가 전부 삭제됐습니다.

#### 반환값

| 필드 | 의미 |
|---|---|
| `success` | 교체 완료 여부 |
| `state.tool_id` | **실제로 장착된 툴.** 요청과 다를 수 있으므로 호출자는 이 값을 확인 |
| `state.grip_width` | 파지 폭. 예상 범위 밖이면 잘못 집음 |

#### 피드백

`step`: 0=반납 → 1=랙 이동 → 2=픽업 → 3=TCP 설정 → 4=검증

#### 주요 에러

| 코드 | 원인 | 처리 |
|---|---|---|
| `E_GRIP_FAILED` | 툴을 못 집음 | **현재 툴 없음 상태로 확정 발행** 후 ABORT |
| `E_TOOL_DROP` | 이동 중 낙하 | 즉시 정지. **수동 개입 필요** — 자동 복구 금지 |
| `E_SAFETY_BLOCKED` | 안전 결함 | REJECT |

> **툴 낙하는 자동 복구하지 마세요.** 어디에 떨어졌는지 모르는 상태에서 로봇을 움직이면 밟습니다. `active_faults`에 등록하고 사람이 치울 때까지 멈춥니다.
> **UV 툴이 낙하하면 상시 ON 램프가 임의 방향을 비추게 됩니다.** 즉시 전원 차단 후 수습하세요.

## 6. B계층 — 공정 노드

### 6.0 손톱 경계는 어디서 오는가 ★★ (v0.3 신설)

> **v0.2 에서 이 자리에 `scan_node` 가 있었습니다.** 탐침으로 3mm 격자를
> 훑어 손톱(고강성)과 피부(저강성)를 군집으로 갈라내고, 경계 부근만 1mm 로
> 다시 떠서 `boundary_polygon` 을 만들던 노드입니다. **폐지됐습니다.**

#### 무엇이 바뀌었나

| | v0.2 (scan_node) | v0.3 (설정값) |
|---|---|---|
| 경계의 출처 | 매 세션 실측 (2.6~3.9분) | `static_frames.yaml` 에 티칭 (0초) |
| 경계의 모양 | 측정점의 볼록 껍질 | 타원 (`nail_boundary_polygon`) |
| 손 위치가 틀리면 | `E_COARSE_INSUFFICIENT` / `E_SEPARATION_LOW` 로 **공정이 시작되지 않음** | **아무도 모른다.** 그대로 작업한다 |
| 가공 금지 영역 | `forbidden_polygon` (저강성 군집) | **없음** |
| 소요 시간 | 세션당 2.6~3.9분 | 0 |

#### 어디에 정의하나

`nail_bringup/config/static_frames.yaml` 한 파일입니다. 두 부분으로 나뉩니다.

```yaml
frames:
  nail_local_frame:            # ① 손톱이 어디 있는가 → 정적 TF
    parent_frame: base_link
    absolute: true
    x_mm: 325.55               # 손톱 표면 중심 (펜던트 TASK-BASE 실측)
    y_mm: -21.85
    z_mm: 394.80               # ★ z=0 이 손톱 표면이 되도록
    roll_deg: 0.0              # roll/pitch 는 반드시 0
    pitch_deg: 0.0
    yaw_deg: 0.0               # 손톱 길이축이 +X 를 향하도록 티칭

nail_region:                   # ② 손톱이 얼마나 큰가 → 노드 파라미터
  size_x_mm: 16.0              # 길이 (큐티클 → 프리에지)
  size_y_mm: 13.0              # 폭
  boundary_points: 24          # 타원을 몇 각형으로 근사할지
```

#### 어떻게 노드에 전달되나

`test_bringup.launch.py` 가 두 경로로 나눠 넣습니다.

```
static_frames.yaml
   ├─ frames:      → static_transform_publisher → TF: base_link → nail_local_frame
   │                 (`frames` 토큰이 있을 때만!)
   └─ nail_region: → 공정 노드 5개의 파라미터로 주입
                     nail_size_x_mm / nail_size_y_mm / nail_boundary_points
                     (`_nail_region_params`. 값이 없거나 이상하면 launch 실패)
```

각 노드는 이 파라미터로 매번 경계를 만듭니다:

```python
from nail_perception.geometry2d import nail_boundary_polygon
boundary_xy = nail_boundary_polygon(size_x_mm, size_y_mm, n_points)  # 원점 중심 타원
```

**타원(볼록)인 것이 중요합니다.** `sanding_node` 의 `travel_limit_mm` 계산이
쓰는 `ray_polygon_distance` 가 "내부에서 쏘면 전방 교차가 하나뿐"이라는
볼록성을 전제합니다.

#### 좌표계 규약 (전 공정 노드 공통)

| 축 | 의미 | 누가 믿는가 |
|---|---|---|
| 원점 | 손톱 표면의 중심 | 전부 |
| `+X` | 큐티클 → 프리에지 | `sanding_node` (`approach_side: free_edge` = −X) |
| `+Y` | 손톱 폭 방향 | `sanding_node` (`left` = +Y, `right` = −Y) |
| `z = 0` | 손톱 표면 | `coating`/`brushing` (접촉), `stone` (압착 목표) |
| `+Z` | 표면에서 멀어지는 방향 | `curing` (`standoff_mm`), `sanding` (`work_plane_offset_mm`) |

#### ⚠️ 이 변경이 안전에 미치는 영향 — 반드시 읽을 것

1. **틀린 값을 알려주는 장치가 없습니다.** 스캔은 손 위치가 3~4mm만 어긋나도
   `E_COARSE_INSUFFICIENT` 로 멈췄지만, 지금은 티칭값이 손과 무관해도
   그 자리를 그대로 갈고 도포합니다.
2. **경계는 실제 손톱보다 작게 잡으세요.** 경계 밖은 곧 피부이고,
   `sanding_node` 의 `travel_limit_mm` 은 이 경계에서 역산됩니다.
   `travel_limit_margin_mm`(기본 2.0)이 유일한 완충입니다.
3. **`forbidden_polygon` 이 사라졌습니다.** 큐티클/피부를 "가공 금지"로
   따로 표시할 방법이 없습니다 — 경계 자체를 보수적으로 잡는 것으로만
   대응합니다. `SandSurface.forbidden_margin_mm` 필드도 함께 삭제됐습니다.
4. **손이 매번 같은 자리에 안착해야 합니다.** 안착 지그가 흔들리면 티칭값이
   그만큼 틀어집니다. 지그를 고정하고, 옮겼으면 `nail_local_frame` 을 다시
   티칭하세요.
5. 확인 방법: `ros2 run tf2_ros tf2_echo base_link nail_local_frame` 로 TF 를
   보고, 실기에서는 툴을 뺀 채 `MoveTo(frame_id: 'nail_local_frame',
   target: {x:0,y:0,z:0.005}, linear: true, speed_ratio: 0.05)` 로 손톱
   표면 5mm 위에 실제로 오는지 눈으로 확인하세요.

### 6.1 `sanding_node` (M01) — **수평 접근 (v0.2 개정)**

> **역할**: 손톱 표면에 **수평으로 접근**해 손톱 경계 안쪽만 정접촉력으로 연마한다.
> **담당**: 주은

#### 제공 / 소비

| | 인터페이스 |
|---|---|
| 제공 | `/process/sand` (Action, `SandSurface`) |
| 소비 | **`/skill/lateral_contact`** · `ValidatePrecondition` · `/safety/status` |

> **v0.1에서 바뀐 점**: `ContactPath` → `LateralContact`. 다른 공정 노드와 달리 이 노드만 다른 스킬을 씁니다.
> **v0.3에서 바뀐 점**: `/scan/get_map` 소비 삭제. 경계를 `nail_region`
> 파라미터에서 직접 만듭니다(§6.0). `travel_limit_mm` 계산식은 그대로이나
> **입력이 측정값에서 티칭값으로 바뀌었습니다.**

#### 파라미터

| 이름 | 타입 | 기본 | 단위 | 설명 |
|---|---|---|---|---|
| **[접근]** | | | | |
| `approach_side` | string | `free_edge` | — | `free_edge` / `left` / `right`. 접근 벡터 결정 |
| `work_plane_offset_mm` | double | `0.0` | mm | 표면 기준 작업 평면 높이 |
| `approach_pitch_deg` | double | `0.0` | deg | 접근 벡터의 표면 대비 각도 (0=완전 수평) |
| **[힘]** | | | | |
| `target_force_n` | double | `2.0` `캘` | N | 접근축 유지 접촉력 |
| `max_force_n` | double | `4.0` `캘` | N | 접근축 힘 상한 |
| `jam_force_n` | double | `4.0` `캘` | N | 진행축 걸림 판정 |
| **[경로]** | | | | |
| `passes` | int | `3` | 회 | 반복 패스 수 |
| `step_over_mm` | double | `1.5` | mm | 패스 간 이송 간격 |
| `feed_speed_mms` | double | `8.0` | mm/s | 진행축 이송 속도 |
| `max_duration_s` | double | `60.0` | s | 과연마 방지 시간 상한 |
| **[안전] ★** | | | | |
| `travel_limit_margin_mm` | double | `2.0` | mm | **경계까지 거리에서 뺄 안전 마진** |
| `engagement_depth_mm` | double | `2.0` | mm | **구현 추가(2026-08-24)** — F/T 센서 미작동으로 순응제어 대신 경계 곡선 waypoint 자체를 접근 방향으로 이만큼 밀어 넣어 연마 깊이를 지오메트리로 직접 준다. `travel_limit_mm`을 넘으면 REJECT(NFR-09) |
| ~~`require_dust_collector`~~ | bool | ~~`true`~~ | — | **삭제됨** — 더스트 컬렉터 미장착 |
| **[손톱 경계] ★ v0.3** | | | | launch 가 `nail_region` 에서 주입 (§6.0) |
| `nail_size_x_mm` | double | `16.0` `캘` | mm | 손톱 길이 (X축) |
| `nail_size_y_mm` | double | `13.0` `캘` | mm | 손톱 폭 (Y축) |
| `nail_boundary_points` | int | `24` | 개 | 타원 근사 각수 |

> **v0.3 삭제**: `forbidden_margin_mm`. `forbidden_polygon` 을 만들던 스캔이
> 없어져 채울 근거가 사라졌습니다 (`SandSurface.action` 에서도 삭제).

#### 동작

```
1. 전제조건: safe_to_move · sander 툴 (더스트 컬렉터 인터록 삭제됨)
2. 손톱 경계 생성 (§6.0)
     nail_boundary_polygon(nail_size_x_mm, nail_size_y_mm, nail_boundary_points)
     → 3점 미만이면 REJECT (E_INVALID_GOAL) — 파라미터가 잘못된 것

3. 접근 벡터 산출:
     approach_side에 따라 nail_local_frame 기준 수평 단위벡터 결정
       free_edge → -X (손끝에서 큐티클 방향)
       left      → +Y
       right     → -Y
     approach_pitch_deg만큼 기울임 (기본 0 = 완전 수평)

4. travel_limit_mm 계산 ★
     진입점(경계 위)에서 approach_vector 방향으로 쏜 반직선이
     반대편 경계와 만나는 거리
       travel_limit_mm = 그 거리 − travel_limit_margin_mm
     계산 결과가 0 이하면 ABORT (E_INVALID_GOAL)
     ※ 이 값이 유일한 피부 접촉 방어선입니다 (§5.1 경고 참조)
     ※ v0.3: 그 "경계"가 티칭값이므로, 이 방어선의 신뢰도 = 티칭 정확도
     engagement_depth_mm이 이 값을 넘으면 ABORT(E_INVALID_GOAL) — NFR-09 초과 위험

5. 경로 생성 ★ (구현 변경, 2026-08-24 — 힘 센서 미작동 대응)
     손톱 경계 다각형(boundary_xy) 중 진입점 쪽 절반을 이송축(feed_axis)
     순서로 뽑아 그 곡선 자체를 waypoint로 쓰고, approach_vector 방향으로
     engagement_depth_mm만큼 offset해 왕복 경로를 만든다.
     (예전 방식: step_over_mm 간격의 직선 왕복 + LateralContact 순응제어로
     곡률 추종 — F/T 센서가 힘을 인식 못 해 폐기됨. 이제 연마 깊이는
     waypoint 좌표 자체가 결정한다.)
     자세는 face-down 고정 quaternion(brushing/coating과 동일) — identity
     자세를 쓰면 nail_local_frame 실측 좌표(B≈±180°)와 반대라 큰 재정렬
     ABORT가 실기에서 확인됨.

6. LateralContact 호출
     approach_vector, waypoints(이미 engagement_depth_mm만큼 눌러 넣은 좌표),
     target_force_n, max_force_n, jam_force_n 전달.
     travel_limit_mm은 이중 압입 방지를 위해 0.1(검증 통과용 최소값)만 전달
     — 실제 진입 깊이는 waypoints가 이미 포함하고 있다.
     ※ robot_skill_node의 lateral_force_sensing_enabled 기본값이 false라
     접촉 탐색/순응제어/힘·저항 감시는 현재 동작하지 않는다(§5.1 참고) —
     이 좌표 기반 경로가 사실상 유일한 안전장치다.

7. passes 만큼 반복 (누적 시간이 max_duration_s 넘으면 중단)
8. 결과 집계
```

> **왜 수평 접근인가**: 샌딩 비트를 손톱 법선 방향으로 누르면 국소 압력이 한 점에 집중되어 표면이 파입니다. 표면에 평행하게 대고 옆으로 밀면 접촉이 선(line)으로 분산되어 균일하게 깎입니다. 실제 시술에서 파일을 눕혀 쓰는 것과 같은 이유입니다.

> **⚠️ 수평 접근의 대가: 강성 감시를 못 씁니다.**
> `ContactPath`와 달리 압입을 하지 않으므로 `E_LOW_STIFFNESS`가 발동하지 않습니다. 피부 접촉을 막는 것은 **4번에서 계산한 `travel_limit_mm` 하나뿐**입니다.
> 따라서 `travel_limit_margin_mm`를 줄이거나 계산을 생략하면 **이 공정에는 안전장치가 아예 없어집니다.** NFR-09(침범 0건)가 이 한 줄에 걸려 있습니다.
>
> **v0.3 에서 이 한 줄이 더 얇아졌습니다.** 예전에는 계산의 입력이 실측
> 경계였고, 손 위치가 틀리면 스캔 단계에서 먼저 걸렸습니다. 지금 입력은
> §6.0 의 티칭값이며 **그것이 맞는지 검증하는 단계가 없습니다.**

> **v0.3 삭제**: `E_NO_SCAN`. 스캔이 없으므로 "스캔 안 됨" REJECT 자체가
> 사라졌습니다. 대신 경계 파라미터가 무효면 `E_INVALID_GOAL` 로 REJECT 합니다.

#### 반환값

| 필드 | 호출자의 판단 |
|---|---|
| `mean_force` / `max_force` | 접근축 힘을 유지했는가 (M01 성공 기준) |
| `max_travel_mm` | **한계 대비 실제 최대 진행 거리.** 여유가 1 mm 미만이면 궤적 재설계 |
| `computed_travel_limit_mm` | 이번 세션에 적용된 한계값 (리포트 기록용) |
| `max_jam_force_n` | 모서리 걸림 정도 |
| `passes_done` / `duration_s` | 사이클 타임, 과연마 여부 |
| `abort_reason` | `ABORT_LATERAL_LIMIT`면 **경계 초과 진행 시도** — 원인 분석 필수 |

#### 피드백

`progress` + `current_wrench` + `travel_mm`, 20 Hz.
→ 웹에 힘 그래프(목표 유지선)와 **진행 거리 게이지(한계 대비)**를 함께 표시.

#### 주요 에러

| 코드 | 원인 | 처리 |
|---|---|---|
| `E_INVALID_GOAL` ★ | `nail_size_*` 파라미터 무효 → 경계 생성 실패 | **REJECT.** 로봇 무동작 |
| `E_LATERAL_LIMIT` ★ | 접근축 한계 초과 | 즉시 역방향 후퇴 + ABORT. **NFR-09 위반 기록** |
| `E_LATERAL_JAM` | 진행축 저항 급증 | 후퇴 + ABORT. 접근각·step_over 재검토 |
| `E_OVERFORCE` | 접근축 과압 | 후퇴 + ABORT. 과연마 방지 |
| `E_INVALID_GOAL` | `travel_limit_mm` ≤ 0 | REJECT. 접근 방향 또는 마진 재설정 |
| `E_INVALID_GOAL` | `engagement_depth_mm` > `travel_limit_mm` | REJECT. NFR-09 초과 위험 |

~~`E_PRECOND_FAILED` (더스트 컬렉터 OFF)~~ — **삭제됨**, 더스트 컬렉터 미장착.

### 6.3 `coating_node` (M03)

> **역할**: 경계에서 안쪽으로 오프셋한 영역에만 젤을 도포한다.
> **담당**: 해윤

#### 동작

```
1. 전제조건: uv 툴 장착
2. 경로 생성
     손톱 경계(§6.0) 전체를 dwell_points 개로 균등 분할
     → 요청한 개수가 나올 때까지 격자를 좁힌다
       (조사 지점 수 = 총 노출량이므로 개수를 반드시 채운다)
     → nail_local_frame 기준 standoff_mm 높이 유지
3. entry_direction에 따라 접근 경로 결정
     → 대기점에서 손톱까지 최단·최소노출 경로 (아래 경고 참조)
4. dwell_points 순회
     각 지점에서 dwell_s_per_point 만큼 정지 체류
     ※ 램프는 이미 켜져 있으므로 "정지 = 조사"
5. 총 체류 시간 집계 → actual_exposure_s
6. park_distance_mm 밖 대기 위치로 이탈
```

> **⚠️ 상시 ON의 부작용: 접근·이탈 경로에서도 조사됩니다.**
> 램프를 켠 채 들고 이동하므로, 손톱으로 접근하는 동안과 빠져나가는 동안에도 UV가 젤에 닿습니다. 결과적으로 **`actual_exposure_s`가 실제 조사량보다 작게 기록**됩니다.
>
> 대응 두 가지 중 하나를 선택하세요.
> 1. **차광 슈라우드 장착 (권장)**: 램프 헤드에 3D 프린팅으로 원뿔형 가림막을 씌워 빔을 좁힙니다. 사전 노출과 주변 산란을 동시에 줄이고, 부품 원가는 필라멘트 값뿐입니다.
> 2. **경로 설계로 회피**: `entry_direction`을 손톱 반대편에서 진입하도록 잡고, `park_distance_mm`를 충분히 확보합니다. 완전히 막지는 못합니다.
>
> 1번을 권합니다. 정량 데이터의 신뢰도와 작업자 노출이 함께 개선됩니다.

#### 반환값

| 필드 | 의미 |
|---|---|
| `actual_exposure_s` | **체류 시간 합계.** 접근·이탈 중 노출은 포함되지 않음 (위 경고 참조) |

#### 피드백

`progress` + `current_dwell_index` + `elapsed_dwell_s`, 10 Hz.

> **v0.1의 `uv_on` 필드는 의미가 없어졌습니다** (항상 true). 대신 `elapsed_dwell_s`를 표시해 "지금 몇 초째 굽고 있는가"를 보여주세요.

## 7. `safety_monitor` ★★

> **역할**: 안전 상태를 감시하고 전제조건을 검증한다.
> **담당**: 희재

### 7.0 ⚠️ v0.2 UV 정책 변경 — 반드시 읽을 것

**v0.1에서는 `safety_monitor`가 UV Digital Output을 단독 소유하고 permit 없이는 점등이 불가능했습니다. v0.2에서는 이 구조가 폐지되고 램프가 상시 ON으로 동작합니다.**

이는 실습 편의를 위한 결정이며, 결과적으로 **소프트웨어 안전 계층이 UV에서 완전히 사라집니다.** 즉:

- E-Stop을 눌러도 **소프트웨어는 램프를 끄지 못합니다**
- 툴을 파지한 채 이동하는 동안에도 램프는 켜져 있습니다
- 노드가 죽거나 통신이 끊겨도 램프는 계속 조사합니다

따라서 **아래 물리적 통제가 이제 유일한 방어선**입니다. 하나라도 빠지면 방어선이 없습니다.

| # | 통제 | 상태 |
|---|---|---|
| 1 | 작업 영역을 UV 차단 아크릴(황색)로 차폐 | **필수** |
| 2 | 작업자·촬영자 전원 UV 차단 고글 착용 | **필수** |
| 3 | 램프 헤드 차광 슈라우드 (§6.5 권장안) | **강력 권장** |
| 4 | 램프 전원선을 **E-Stop 회로에 직렬 결선** (하드웨어) | **강력 권장** |
| 5 | 수동 마스터 스위치를 작업자 손 닿는 곳에 배치 | **필수** |
| 6 | 미사용 시 UV 툴을 랙에 **광축이 랙 안쪽을 향하도록** 반납 (`uv_park_facing`) | **필수** |

> **4번은 permit 폐지와 모순되지 않습니다.** permit은 소프트웨어 승인 절차이고, 4번은 전원 라인 물리 결선입니다. 배선 하나로 "E-Stop 누르면 램프도 꺼진다"가 복원되므로, 가능하면 반드시 하세요. **소프트웨어를 못 믿는 상황일수록 하드웨어 인터록의 값이 올라갑니다.**
>
> 365/405 nm는 통증이 지연되어 나타나므로 노출을 인지하기 어렵습니다. 실습 중 "잠깐인데 괜찮겠지"가 가장 위험합니다.

### 동작

**① 상태 수집 루프 (`publish_rate_hz`)** — **구현: DI 대신 `robot_state` 폴링 하나로 통합**

```
/tool/status 최신값 반영
safe_to_move = (not estop) and comm_ok and (active_faults 비어 있음)
→ SafetyState 발행
```

**② E-Stop 처리 (최우선)** — **구현: DI 상승 대신 `robot_state` 진입 에지**
```
robot_state 가 EMERGENCY_STOP(6/7)으로 전이하는 에지 감지
   ① safe_to_move = false 발행
   ② ABORT 래치 설정 (ResetSafety 전까지 유지)
   ③ FAULT_ESTOP을 active_faults에 등록
```

> **v0.1에는 "UV DO OFF를 모션 정지보다 먼저"라는 항목이 ①에 있었습니다. v0.2에서는 소프트웨어가 UV를 끌 수 없으므로 이 단계가 사라졌습니다.** §7.0의 4번(하드웨어 결선)이 이 역할을 대신합니다.

**③ 전제조건 검사 (`ValidatePrecondition`)** — **구현: 안착/더스트 항목 전부 삭제, `safe_to_move` + 요구 툴만 검사**

|---|---|
| SAND | `safe_to_move` · sander 툴 |
| BRUSH | `safe_to_move` · brush 툴 |
| COAT | `safe_to_move` · coater 툴 |
| CURE | `safe_to_move` · uv 툴 |
| STONE | `safe_to_move` · tweezers 툴 |

> **v0.3 삭제**: `SCAN` · `INSPECT` 스테이지 상수와, 모든 스테이지의
> "스캔 valid" 조건. 손톱 경계는 이제 런타임 상태가 아니라 설정값이라
> `safety_monitor` 가 검증할 대상이 아닙니다 — 각 공정 노드가 자기

### 동작

**손가락 1개(D-07)이므로 반복은 레이어 하나뿐입니다.**

```
PRECHECK  → 통신 · E-Stop 해제 · 툴 랙 설정 전수 확인 (안착 확인은 삭제됨 — 안착 센서 미장착)

   ↓
SAND      → ChangeTool(sander) → 경유점 → sander_work → 수평 연마

BRUSH     → ChangeTool(brush)  → 경유점 → brush_work  → 더스트 제거  [enable_brush]
```

> 젤로 먼저 캘리브레이션**하고 첫 레이어 후에는 사람이 눈으로 확인하세요.

> **툴 교체 횟수가 줄었습니다.** v0.2 는 레이어당 `coater → uv → probe` 3회,
> `layer_total=2` 기준 총 9회였습니다. v0.3 은 레이어당 `coater → uv` 2회,
> 총 **6회**(sander, brush, coater×2, uv×2 + 마지막 반납). 교체 1회 15초면
> 약 45초를 아낍니다 — 스캔(2.6~3.9분)과 검사가 통째로 빠진 것은 별도입니다.
>
> **v0.2에서 UV 상시 ON이 되면서 D-05(UV 손목 상시 장착, C안)의 성격이 바뀌었습니다.** 상시 장착하면 교체가 레이어당 2회로 줄지만, **켜진 램프를 계속 손목에 달고 전 공정을 도는 것**이 됩니다. 연마·도포 중에도 UV가 작업 영역을 비추게 되어, 도포한 젤이 의도치 않게 굳습니다. **v0.2 조건에서는 C안을 권장하지 않습니다.** 랙 반납 방식을 유지하세요.

### 피드백

`ProcessState` 전체를 그대로 실어 보냅니다. 상태 전이 시 즉시 + 1 Hz.
`/process/status` 토픽에도 **같은 내용을 동시 발행**합니다.

> **왜 둘 다 발행하나**: 액션 feedback은 goal을 보낸 클라이언트만 받습니다. 웹 화면 여러 개가 동시에 볼 수 있으므로 토픽도 필요합니다.

### 주요 에러

| 코드 | 원인 | 처리 |
|---|---|---|
| `E_PRECOND_FAILED` | PRECHECK 실패 (툴랙 설정·통신·E-Stop) | 즉시 ABORT |
| `E_SAFETY_BLOCKED` | 실행 중 안전 결함 | **하위 액션 전부 cancel** 후 ABORT |
| `E_CANCELLED` | 사용자 취소 (BR-16) | 하위 cancel → 툴 반납 → HOME |

**ABORT 공통 처리**
```
① 진행 중인 하위 액션 전부 cancel (완료 대기)
② 툴을 들고 있으면 ChangeTool("none")으로 반납 시도
     ※ UV 툴이면 반납 우선순위 최상 — 켜진 램프를 들고 멈추면 안 됨
③ HOME 복귀
④ ProcessState(stage=STAGE_ABORTED) 발행
⑤ 자동 재시작 안 함 (NFR-06)
```

> **②에서 반납이 실패해도 ③은 진행해야 합니다.** 단, **UV 툴 반납 실패는 예외적으로 심각합니다** — 켜진 램프를 든 채 HOME으로 가면 이동 경로 전체가 조사됩니다. UV 반납 실패 시에는 HOME 복귀 대신 **현재 위치에서 정지하고 수동 개입을 요청**하세요(램프를 사람이 끄거나 회수). 반납 실패는 `active_faults`에 남깁니다.

| **[동역학]** | | | | |
| `motion_lag_tau_s` | double | `0.15` | s | 1차 지연 시정수 |
| `speed_scale` | double | `1.0` | — | **>1이면 시뮬레이션 가속** (테스트 시간 단축) |

### 합성해야 할 데이터

| 신호 | 합성 방식 |
|---|---|
| TCP 자세 | 명령 자세로 1차 지연(`motion_lag_tau_s`) 후 수렴 |
| Fz (접촉 전) | 노이즈만 (`noise_sigma_n`) |
| Fz (접촉 후) | `F = k × (z_cmd − z_surface)` + 노이즈 |
| 강성 `k` | 타원 내부면 `k_nail`, 외부면 `k_skin`, 경계는 `k_transition_mm` 폭으로 부드럽게 전이 |
| **수평 접촉력** | 접근 벡터 방향 진행량에 비례. 타원 경계 넘으면 저항 급증(`lateral_jam` 재현) |
| 택프리 릴리즈 | `cured=false` 또는 `uncured_region`에 해당하면 이탈 시 음의 Fz 주입 |

> **⚠️ v0.3: 이 장은 대부분 스캔·검사를 전제로 쓰였습니다.**
> `nail_center_offset_mm`(스캔이 오프셋을 찾아내는지), `uncured_region`(REWORK
> 루프 시험), `k_transition_mm`(강성 전이로 `separation_margin` 검증) 은 전부
> 폐지된 노드를 위한 기능이라 **더 이상 만들 이유가 없습니다.**
>
> v0.3 에서 mock 이 여전히 유용한 부분은 강성/접촉력 합성(ContactPath·
> LateralContact 의 힘 추종과 `travel_limit_mm` 동작 확인)과 `inject_fault`
> 뿐입니다. 그리고 이 워크스페이스에는 **`mock_robot_driver` 가 실제로
> 배선돼 있지 않습니다** — `use_mock_hardware` 파라미터는 선언만 돼 있고
> `DsrAdapter` 에 mock 분기가 없습니다. 로봇 없이 돌리려면 두산 공식 가상
> 모드(`dsr_bringup2 mode:=virtual`)를 쓰세요.

`inject_fault`가 있으면 **인터록 테스트를 로봇 없이 대부분 돌릴 수 있습니다.**

### 12.3 파일 배치

**실제 워크스페이스의 배치는 위 계획보다 훨씬 단순합니다** — 노드별
yaml 을 만들지 않고, launch 인자와 세 개의 설정 파일로 끝냅니다.

```
nail_bringup/config/
└── static_frames.yaml       ★ nail_local_frame(TF) + nail_region(손톱 크기)
                               → `frames` 토큰 + 공정 노드 5개 파라미터 (§6.0)

nail_skill/config/
├── targets.yaml             툴 랙 좌표 · <툴>_work · rack_transit · stone_tray
└── tool_rack.yaml           툴 카탈로그 (slot_frame · 파지 폭 · TCP 오프셋)

nail_bridge/config/
└── web_bridge.yaml          rosbridge 화이트리스트 (중계 토픽 3개)
```

나머지 파라미터는 `test_bringup.launch.py` 의 `DeclareLaunchArgument` 로
노출돼 있습니다 (`heartbeat_timeout_ms`, `safety_publish_rate_hz`,
`sync_tcp_on_startup`, `base_frame_id`, `log_level` 등). ~~`require_handrest`~~는
안착 센서 미장착으로 삭제됨.

> ⚠️ **yaml 을 고쳤으면 반드시 다시 빌드하세요.** 세 파일 모두 `install/`
> 아래로 복사된 사본이 로드되고, `targets.yaml` 은 `robot_skill_node` 가
> 첫 조회 때 메모리에 캐시합니다 — 파일만 고치고 노드를 살려두면 옛 좌표가
> 계속 쓰입니다.

> `use_mock_hardware:=true` 는 아직 배선돼 있지 않습니다 (§10 참조).
