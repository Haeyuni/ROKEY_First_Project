## 1. 공통 절차

### 1.1 노드 조합해서 띄우기

```bash
# A계층 substrate만 (가장 자주 씀 — 대부분의 단독 테스트 전제조건)
ros2 launch nail_bringup test_bringup.launch.py
# 위와 동일: nodes:=safety,skill,tool (기본값)

# 특정 공정 노드 하나 추가
ros2 launch nail_bringup test_bringup.launch.py nodes:=safety,skill,tool,sanding

# 스캔까지 필요한 공정(coating/curing/inspection) 테스트 시
ros2 launch nail_bringup test_bringup.launch.py nodes:=safety,skill,tool,scan,coating

# 전체 스택
ros2 launch nail_bringup test_bringup.launch.py nodes:=all
```

토큰은 자동으로 의존성을 끼워 넣지 않습니다 — `scan`을 빼고 `coating`만
띄우면 `GetStiffnessMap` 호출이 실패하는 것 자체가 **REJECT(E_NO_SCAN) 테스트
케이스**입니다. §3부터는 각 노드가 무엇을 함께 띄워야 "정상 케이스"를 볼 수
있는지 표기합니다.

### 1.2 안전 게이트 먼저 확인 (모든 테스트 공통 0단계)

```bash
ros2 topic echo /safety/status --once
```

`safe_to_move: true`, `active_faults: []` 를 확인하기 전에는 어떤 액션도
보내지 마세요. `false`면:

```bash
ros2 service call /safety/reset nail_msgs/srv/ResetSafety \
  "{confirm: true, operator_note: 'unit test reset'}"
```

`remaining_faults`가 비어야 성공입니다 — 안 비면 물리적 원인(안착 센서,
더스트 컬렉터, E-Stop)을 먼저 해소하세요. §7(safety_monitor) 절 참조.

### 1.3 CLI 치트시트

| 하고 싶은 것 | 명령 |
|---|---|
| 액션 보내기 + 피드백 구독 | `ros2 action send_goal <action> <type> "{...}" --feedback` |
| 액션 타입/필드 확인 | `ros2 interface show nail_msgs/action/<Name>` |
| 서비스 호출 | `ros2 service call <srv> <type> "{...}"` |
| 토픽 1회 확인 | `ros2 topic echo <topic> --once` |
| 노드가 실제로 떴는지 | `ros2 node list` / `ros2 node info <node>` |
| 파라미터 실기 튜닝(재시작 없이) | `ros2 param set <node> <param> <value>` |
| 진행 중 액션 취소 | `Ctrl-C` (send_goal 프로세스 종료 시 자동 cancel 요청) |

`ros2 action send_goal`은 goal을 보낸 뒤 결과를 기다리며 블로킹합니다.
피드백을 보려면 반드시 `--feedback`을 붙이세요 — 실기에서 로봇이 움직이는
중에는 피드백 없이 기다리면 멈춘 건지 도는 건지 알 수 없습니다.

### 1.4 판정 공통 규칙 (NIS §3.2)

| 결과 | 관찰 |
|---|---|
| **REJECT** | `send_goal`이 `Goal rejected`로 즉시 끝남. **로봇은 한 번도 안 움직여야 함** |
| **ABORT** | goal은 accept됐다가 `status: ABORTED`로 종료. **이탈 동작(+Z 또는 역벡터) 후 정지했는지 반드시 육안 확인** |
| **CANCEL** | `Ctrl-C` 후 `status: CANCELED`. ABORT와 동일한 뒷정리가 일어나야 함 |

모든 실패 케이스에서 `result.base.error.code`가 NIS §4 표준 코드와
정확히 일치하는지 확인하세요 — 자유 서술 문자열이면 그 자체가 버그입니다.

## 3. `robot_skill_node` (NIS §5.1)

**띄우기**: `nodes:=safety,skill,tool` (그리퍼 검증에 tool_manager도 있는 게
편함) · 사전조건: probe/sander 등 원하는 툴이 실제로 TCP에 물려 있어야
`ProbePoint`/`ContactPath` 등이 의미 있음. `ChangeTool`은 §4에서.

### 3.1 `MoveTo`

```bash
ros2 action send_goal /skill/move_to nail_msgs/action/MoveTo "{
  target: {position: {x: 0.4, y: 0.0, z: 0.3},
           orientation: {x: 0.0, y: 1.0, z: 0.0, w: 0.0}},
  frame_id: 'base_link', linear: true,
  speed_ratio: 0.1, accel_ratio: 0.1, timeout_s: 15.0
}" --feedback
```

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 정상 이동 | 위 명령, 안전한 빈 공간 좌표 | `success=true`, `position_error_mm` < `move_pose_tolerance_mm`(기본 1.0) |
| 안전 차단 | E-Stop 누른 채로 goal 전송 | REJECT, `error.code=E_SAFETY_BLOCKED` |
| 타임아웃 | `timeout_s: 0.01`로 먼 좌표 | ABORT, `error.code=E_TIMEOUT` 또는 `E_MOTION_FAILED` |

### 3.2 `PickPlace` — `/skill/pick_place`

`target_key`는 `robot_skill_node`의 `targets_yaml_path`(`nail_skill/config/targets.yaml`)
키 또는 TF 프레임명 — 둘 중 targets.yaml에 먼저 있으면 그게 쓰이고, 없으면
target_key 자체를 TF 프레임 이름으로 취급한다. `mode`는 `pick`/`place`.

```bash
ros2 action send_goal /skill/pick_place nail_msgs/action/PickPlace "{
  mode: 'pick', target_key: 'probe', frame_id: 'base_link',
  approach_height_mm: 20.0, grip_width_mm: 18.0,
  expected_width_mm: 18.0, width_tolerance_mm: 1.0, verify_grip: true
}" --feedback
```

> ⚠️ **툴 랙 슬롯(`slot_1`~`slot_6`)은 아직 테스트할 수 없습니다.**
> `tool_manager`가 `target_key`로 넘기는 `slot_frame`(예: `slot_2`)은
> `targets.yaml`에 없어 TF 프레임으로 폴백 조회되는데, NIS §11.4가 요구하는
> `tool_rack_frame`/`slot_*` static_transform_publisher가 이 저장소 어디에도
> 아직 구현돼 있지 않습니다(실측 확인 — 현재 TF 트리는 `world → base_link →
> link_1..6 → tool0 → rg2_*`뿐). `ChangeTool`/`slot_*` 대상 `PickPlace`는 이게
> 세팅되기 전까지 전부 `E_INVALID_GOAL`(TF lookup 실패)로 ABORT됩니다 — 노드
> 버그가 아니라 아직 채워지지 않은 인프라입니다. `targets.yaml`에 등록된
> `stone_tray` 같은 키로 먼저 인터페이스 동작을 확인하세요.

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 정상 픽 | 실제로 물건이 있는 슬롯 | `grip_verified=true`, `measured_width_mm`가 `expected_width_mm` ± `width_tolerance_mm` 안 |
| 빈 슬롯 파지 실패 | 물건 없는 슬롯 지정 | ABORT, `error.code=E_GRIP_FAILED` — **그리퍼가 열린 채 후퇴하는지 육안 확인** |
| 이동 중 낙하 (수동 재현 어려움) | 파지 후 사람이 살짝 건드려 폭 변화 유도 | ABORT, `error.code=E_TOOL_DROP`, **즉시 정지** — 자동 복구하면 버그 |

### 3.3 `ContactPath` — `/skill/contact_path`

법선(+Z 이탈) 접근. brushing/coating이 내부적으로 쓰는 것과 동일 인터페이스를
직접 두드려 저수준으로 확인.

```bash
ros2 action send_goal /skill/contact_path nail_msgs/action/ContactPath "{
  waypoints: [{position: {x: 0.40, y: 0.0, z: 0.20}, orientation: {w: 1.0}},
              {position: {x: 0.41, y: 0.0, z: 0.20}, orientation: {w: 1.0}}],
  frame_id: 'nail_frame', session_id: 'unit_test',
  target_force_n: 0.5, max_force_n: 20.5, feed_speed_mms: 5.0,
  use_compliance: true, abort_on_low_stiffness: false,
  min_stiffness_n_per_mm: 0.0, allowed_polygon: [], passes: 1,
  max_duration_s: 20.0
}" --feedback
```

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 정상 접촉 추종 | 위 명령, 실제 표면 위 좌표 | `mean_force_n` ≈ `target_force_n`, `abort_reason=''` |
| 표면 미검출 | `contact_search_max_depth_mm`보다 훨씬 위 좌표(허공) | ABORT, `error.code=E_NO_CONTACT` |
| 과압 | `max_force_n: 0.2`로 낮게, `target_force_n: 0.5` (모순 유도) | ABORT, `error.code=E_OVERFORCE`, `abort_reason` 포함 — **+Z로 후퇴하는지 육안 확인** |
| 저강성(피부 의심) | `abort_on_low_stiffness: true`, `min_stiffness_n_per_mm`을 실제 강성보다 높게 | ABORT, `error.code=E_LOW_STIFFNESS` — **이 케이스는 반드시 안전한 더미(진짜 피부 아님) 위에서만** |

### 3.4 `LateralContact` — `/skill/lateral_contact` ★ (v0.2 신설, sanding 전용)

> ⚠️ NIS §5.1 경고: 이 액션은 강성 감시가 없습니다. **`travel_limit_mm` 하나가
> 유일한 방어선**입니다. 처음 테스트할 때는 반드시 `travel_limit_mm`을 작게
> (2~3 mm) 잡고, 손이 아니라 지그/더미 손톱 위에서 하세요.

```bash
ros2 action send_goal /skill/lateral_contact nail_msgs/action/LateralContact "{
  approach_vector: {x: -1.0, y: 0.0, z: 0.0},
  waypoints: [{position: {x: 0.40, y: 0.0, z: 0.20}, orientation: {w: 1.0}}],
  frame_id: 'nail_local_frame', session_id: 'unit_test',
  work_plane_offset_mm: 0.0, target_force_n: 1.0, max_force_n: 2.0,
  jam_force_n: 3.0, feed_speed_mms: 3.0,
  travel_limit_mm: 3.0, retreat_mm: 5.0, passes: 1, max_duration_s: 20.0
}" --feedback
```

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 정상 수평 접촉 | 위 명령 | `mean_force_n` ≈ `target_force_n`, `max_travel_mm` ≤ `travel_limit_mm` |
| 접근축 한계 초과 ★ | `travel_limit_mm: 0.5`(고의로 작게) | ABORT, `error.code=E_LATERAL_LIMIT`, `abort_reason=ABORT_LATERAL_LIMIT` — **역방향(접근벡터 반대)으로 `retreat_mm`만큼 후퇴하는지 육안 필수 확인** — 이게 안 되면 §5.1 안전 경고가 실제로 뚫려 있는 것 |
| 진행축 걸림 | 모서리 근처로 waypoints 설정, `jam_force_n`을 낮게 | ABORT, `error.code=E_LATERAL_JAM` |
| goal 자체 무효 | `travel_limit_mm: 0.0` | REJECT, `error.code=E_INVALID_GOAL` (로봇 안 움직여야 함) |

### 3.5 `ProbePoint` — `/skill/probe_point`

스캔·검사가 공유하는 최소 단위. `stiffness`가 하강 구간 선형회귀로 나오는지
직접 확인.

```bash
ros2 action send_goal /skill/probe_point nail_msgs/action/ProbePoint "{
  target: {x: 0.40, y: 0.0, z: 0.20}, frame_id: 'nail_frame',
  approach_height_mm: 20.0, probe_speed_mms: 2.0,
  contact_threshold_n: 0.3, max_depth_mm: 1.0, max_force_n: 3.0,
  lateral_force_limit_n: 5.0, measure_release: true,
  release_speed_mms: 1.0, source_tag: 'unit_test'
}" --feedback
```

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 정상 압입 | 손톱 위 | `point.contacted=true`, `point.stiffness_n_per_mm` > 0, `regression_samples ≥ probe_regression_min_samples`(기본 10) |
| 표면 없음 | 허공 좌표 | `point.contacted=false`, ABORT `E_NO_CONTACT` |
| 이탈력 측정 | `measure_release: true`, 접착력 있는 표면(예: 덜 마른 젤 더미) | `point.release_force_n` < 0 확인 |

## 4. `tool_manager` (NIS §5.2)

**띄우기**: `nodes:=safety,skill,tool`

> ⚠️ **지금은 이 액션 전체가 막혀 있습니다.** §3.2 박스 참조 — 랙 슬롯
> TF(`slot_1`~`slot_6`)가 아직 없어 `ChangeTool`은 어떤 툴을 요청해도
> `E_INVALID_GOAL`로 ABORT됩니다. static_transform_publisher가 세팅된
> 뒤에만 아래 케이스를 실행하세요.

```bash
ros2 action send_goal /tool/change nail_msgs/action/ChangeTool "{
  target_tool: 'probe', expected_width_mm: 0.0, width_tolerance_mm: 1.0,
  verify_after_grip: true, park_facing: 'into_rack'
}" --feedback

ros2 service call /tool/get_info nail_msgs/srv/GetToolInfo "{tool_id: ''}"
```

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 정상 교체 | 위 명령 | `state.tool_id='probe'`, `feedback.step`이 0→4로 순서대로 발행, `/tool/status` 최신값 갱신(`ros2 topic echo /tool/status --once`) |
| 반납만 | `target_tool: 'none'` (이미 툴 든 상태에서) | 현재 툴 랙 반납, `state.tool_id='none'` |
| 툴 미인식/파지 실패 | 랙에 툴이 없는 슬롯으로 시험 유도 | ABORT, `error.code=E_GRIP_FAILED`, **`/tool/status`가 "현재 툴 없음"으로 확정 발행되는지 확인** (NIS §5.2 경고) |
| UV 반납 자세 | `target_tool:'uv'`로 픽업 후 다시 `'none'`으로 반납, `park_facing:'into_rack'` | 반납 시 광축이 랙 안쪽을 향하는지 **육안 확인** (§7.0 통제 #6, UV 상시 ON이므로 필수) |

## 5. `safety_monitor` ★★ (NIS §7)

**띄우기**: `nodes:=safety,skill,tool`

### 5.1 상태 발행

```bash
ros2 topic hz /safety/status        # publish_rate_hz(기본 20)와 일치하는지
ros2 topic echo /safety/status --once
```

### 5.2 `ValidatePrecondition` — 스테이지별

```bash
ros2 service call /safety/validate nail_msgs/srv/ValidatePrecondition \
  "{stage: 'SAND', session_id: 'unit_test', required_tool: 'sander'}"
```

| stage | 필요 조건 (§7 표) | 테스트 |
|---|---|---|
| `SCAN` | 안착 + probe 툴 | probe 미장착 상태로 호출 → `ok=false`, `blocking_reasons`에 툴 사유 포함 |
| `SAND` | 안착 + sander 툴 + 더스트 컬렉터 ON + 스캔 valid | 더스트 컬렉터 OFF 상태로 호출 → `blocking_reasons`에 더스트 사유 포함 |
| `COAT`/`CURE`/`INSPECT` | + 스캔 valid | 스캔 전 상태로 호출 → 스캔 무효 사유 포함 |

**`blocking_reasons`는 항상 배열 전체를 확인하세요** — 막힌 이유가 여러
개일 때 하나만 주면 그 자체가 §7 규약 위반입니다.

### 5.3 E-Stop 처리 (물리 테스트, 필수)

1. 로봇이 정지 상태인지 확인 후 **실제 E-Stop 버튼**을 누른다.
2. `ros2 topic echo /safety/status --once` → `safe_to_move=false`,
   `active_faults`에 `FAULT_ESTOP` 포함, `estop_released=false` 확인.
3. 이 상태에서 아무 공정 액션이나 `send_goal` → **REJECT**되는지 확인
   (§3.4 안전 규약 — 이미 실행 중이던 액션이 있었다면 ABORT).
4. E-Stop 해제 → `ResetSafety` 호출 (§1.2) → `remaining_faults=[]`,
   `safe_to_move=true` 복귀 확인.

> **`auto_reset` 파라미터가 `false`인지 반드시 확인**하세요
> (`ros2 param get safety_monitor auto_reset`). `true`면 이 노드의 존재
> 의미가 사라진다고 NIS §7이 명시합니다 — 단위 테스트 항목 중 유일하게
> "값이 바뀌어 있으면 그 자체가 실패"인 파라미터입니다.

### 5.4 인터록 개별 확인

| 인터록 | 유발 방법 | 기대 |
|---|---|---|
| 안착 센서(`FAULT_NO_HANDREST`) | 손목/손 지그를 안착 센서에서 뗌 | `safe_to_move=false`, 재안착 시 자동 복귀(래치 아님, E-Stop과 다름) |
| 더스트 컬렉터(`FAULT_NO_DUST`) | 컬렉터 전원 OFF | SAND 스테이지 `ValidatePrecondition`이 `ok=false` |
| 통신 두절(`FAULT_COMM_LOST`) | 컨트롤러 네트워크 케이블 순간 분리 (팀과 상의 후) | `heartbeat_timeout_ms`(기본 200 ms) 경과 후 `comm_ok=false` |

## 13. `session_orchestrator` — 통합 스모크 테스트 (NIS §8)

개별 노드 단위 테스트가 모두 통과한 뒤에만 진행하세요. 이 노드는 로봇을
직접 움직이지 않고 위 노드들을 순서대로 호출만 합니다 — 여기서 나는 실패는
대부분 "개별 노드는 되는데 조합 순서/타임아웃이 안 맞는" 문제입니다.

```bash
ros2 action send_goal /session/run nail_msgs/action/RunSession "{

  shape_profile_id: 'default', target_material: 'test_jig',

```

- `/process/status`를 별도 터미널에서 `ros2 topic echo`로 같이 보면서

- 취소 테스트: 중간에 `Ctrl-C` → 하위 액션까지 전부 cancel되고, 툴이

  재조사되는지, `total_rework`가 `max_rework` 넘으면 `E_REWORK_EXCEEDED`로
  ABORT하는지 확인.

## 14. 완료 판정 체크리스트

각 노드 테스트를 "끝냈다"고 선언하기 전에 (NIS §13과 별개로, 이 문서 기준):

- [ ] 정상 케이스 1개 이상 `success=true`로 통과
- [ ] 그 노드의 ★ 표시된 안전 관련 에러 케이스가 실제로 재현되고, 문서에 적힌
      이탈/후퇴 동작이 **육안으로** 확인됨
- [ ] `result.base.error.code`가 NIS §4 표준 코드와 정확히 일치
- [ ] 모든 ABORT 로그에 에러 코드 + 좌표/측정값이 있음 (`ros2 topic echo /rosout`)
- [ ] `/safety/status` 구독 반응(safe_to_move=false 시 REJECT/ABORT)을 최소 1회 확인
- [ ] 테스트 후 로봇을 HOME 또는 안전 위치로 복귀시키고, 장착 중이던 툴을 반납함
