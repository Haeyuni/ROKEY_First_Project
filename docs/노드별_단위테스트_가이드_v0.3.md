## 0. 전제

- 이 워크스페이스에는 mock 하드웨어 경로가 배선되어 있지 않습니다
  (`use_mock_hardware`는 선언만 되어 있고 `DsrAdapter`에 mock 분기가 없음).
  **모든 테스트는 실기 위에서 진행합니다.** 안전 게이트(§1.2)를 먼저 확인하고,
  각 액션은 피드백을 보며 사람이 지켜보는 상태에서 한 번씩 보내고, 힘/속도
  파라미터는 낮은 값에서 시작해 실기에서 올립니다.

- `robot_skill_node` / `tool_manager` / `safety_monitor` 는 **`ws_dsr`를
  source하지 않으면 프로세스가 즉시 죽습니다** (`DSR_ROBOT2` import 실패).
  매 터미널마다:
  ```bash
  source /opt/ros/<distro>/setup.bash
  source ~/ws_cobot_pjt/ws_dsr/install/setup.bash   # dsr_common2, dsr_msgs2, onrobot_rg_msgs
  source ~/ws_cobot_pjt/ws_cobot1/install/setup.bash
  ```

- **설정 파일(yaml)을 고쳤으면 반드시 다시 빌드하고 노드를 재시작하세요.**
  yaml은 `install/` 아래로 복사되어 로드되고, `targets.yaml`은 노드가
  첫 조회 때 메모리에 캐시합니다(`_targets_cache`) — 파일만 고치고 노드를
  살려두면 **옛 좌표가 계속 쓰입니다.**
  ```bash
  colcon build --packages-select nail_msgs nail_perception nail_skill nail_process nail_orchestrator nail_safety nail_bringup
  source install/setup.bash
  ```
  > ⚠️ **v0.3 은 `nail_msgs` 를 반드시 다시 빌드해야 합니다.** 메시지 8종이
  > 삭제되고 여러 액션의 필드가 바뀌었습니다. 예전 빌드 산출물이 남아 있으면
  > 노드가 `AttributeError` 나 import 실패로 죽습니다. 확실히 하려면
  > `rm -rf build install log` 후 전체 빌드하세요.

- 노드가 뜨는 것과 액션이 도는 것은 다릅니다. `DsrAdapter`는 두산 서비스
  디스커버리에 실패해도 WARN만 찍고 계속 뜨므로, **`dsr_bringup2`(+ 그리퍼
  드라이버)가 실제로 켜져 있는지 매번 눈으로 확인**하세요
  (`ros2 node list`에 `/dsr01/dsr_controller2`가 보여야 함).

- **반드시 launch로 띄우세요.** `ros2 run`으로 직접 띄우면 `base_frame_id`가
  노드 기본값 `base_0`으로 남는데, 이 드라이버가 실제 발행하는 루트 프레임은
  `base_link`입니다 — `targets.yaml`의 `frame_id: base_link`와 어긋나 TF 변환
  실패로 모든 PickPlace가 `E_INVALID_GOAL`이 됩니다. launch는 이 값을
  `base_link`로 덮어씁니다.
  **v0.3 추가**: 공정 노드를 `ros2 run` 으로 띄우면 `nail_size_*` 파라미터도
  주입되지 않아 노드 기본값(16×13mm)이 쓰입니다.

## 1. 공통 절차

### 1.1 노드 조합해서 띄우기

```bash
# A계층 substrate만 (§3·§4·§5의 전제조건)
ros2 launch nail_bringup test_bringup.launch.py
# 위와 동일: nodes:=safety,skill,tool (기본값)

# 공정 노드 — frames 토큰을 반드시 포함할 것 (§6)
ros2 launch nail_bringup test_bringup.launch.py nodes:=frames,safety,skill,tool,sanding

# 전체 스택 (frames 포함됨)
ros2 launch nail_bringup test_bringup.launch.py nodes:=all
```

사용 가능한 토큰: `frames` `safety` `skill` `tool` `sanding` `brushing`
`coating` `curing` `stone` `orchestrator` (또는 `all`).

> ⚠️ **`scan` / `inspection` 토큰은 없어졌습니다.** 예전 명령을 그대로
> 복사해 쓰면 launch 가 `알 수 없는 nodes 토큰: ['scan']` 으로 즉시 실패합니다.
> 이건 정상 동작입니다 — 조용히 무시하지 않도록 일부러 막아둔 것입니다.

> ⚠️ **`frames` 토큰 주의.** 토큰은 의존성을 자동으로 끼워 넣지 않습니다.
> `frames`를 빼면 **`nail_local_frame` TF가 발행되지 않아 §7 이후 공정 노드가
> 전부 TF lookup 실패로 ABORT**합니다. 반대로 §3·§4(PickPlace/ChangeTool)는
> `targets.yaml` 좌표를 `base_link` 기준으로 직접 쓰므로 `frames` 없이도
> 동작합니다.
>
> 단, **손톱 크기 파라미터(`nail_size_*`)는 `frames` 토큰과 무관하게** 공정
> 노드가 하나라도 있으면 주입됩니다. `static_frames.yaml` 에 `nail_region:`
> 이 없거나 값이 이상하면 **launch 자체가 뜨지 않습니다** — 틀린 경계로
> 로봇이 도는 것보다 안 뜨는 게 낫다는 설계입니다.

기동 로그에 아래 줄이 보이는지 확인하세요:
```
[nail_bringup] 손톱 작업 영역: 16.0 x 13.0 mm (24각형, nail_local_frame 기준)
```

| 하고 싶은 것 | 명령 |
|---|---|
| 액션 보내기 + 피드백 구독 | `ros2 action send_goal <action> <type> "{...}" --feedback` |
| 액션 타입/필드 확인 | `ros2 interface show nail_msgs/action/<Name>` |
| 서비스 호출 | `ros2 service call <srv> <type> "{...}"` |
| 토픽 1회 확인 | `ros2 topic echo <topic> --once` |

`ros2 action send_goal`은 결과를 기다리며 블로킹합니다. **`--feedback`을
반드시 붙이세요** — 실기에서 피드백 없이 기다리면 멈춘 건지 도는 건지
구분할 수 없습니다.

### 1.4 판정 공통 규칙 (NIS §3.2)

| 결과 | 관찰 |
|---|---|
| **REJECT** | `send_goal`이 `Goal rejected`로 즉시 끝남. **로봇은 한 번도 안 움직여야 함** |
| **ABORT** | goal accept 후 `status: ABORTED`. **이탈 동작(+Z 또는 역벡터) 후 정지했는지 육안 확인** |
| **CANCEL** | `Ctrl-C` 후 `status: CANCELED`. ABORT와 동일한 뒷정리 |

모든 실패 케이스에서 `result.base.error.code`가 NIS §4 표준 코드와 정확히
일치하는지 확인하세요 — 자유 서술 문자열이면 그 자체가 버그입니다.

### 1.5 ⚠️ 이번 판에서 알아야 할 하드웨어 제약

**`grip_verified`는 신뢰할 수 없습니다.** RG2 드라이버가 실제 파지 폭
되읽기를 노출하지 않아, `robot_skill_node`가 **명령값을 그대로**
`measured_width_mm`에 넣어 돌려줍니다:

```python
measured = goal.expected_width_mm                      # robot_skill_node.py
grip_verified = abs(measured - goal.expected_width_mm) <= tol   # → 항상 true
```

따라서:
- **툴을 놓쳐도 `grip_verified=true`, `success=true`가 나옵니다.**
- "빈 슬롯 파지 실패 → `E_GRIP_FAILED`" 케이스는 **재현되지 않습니다**
  (그리퍼 서비스 호출 자체가 실패할 때만 이 코드가 납니다).
- 파지 성공 여부는 **반드시 육안으로** 판정하세요.

관련 함정: `verify_grip`을 false로 두고 `ChangeTool`을 성공시키면
`/tool/status`에 `current_tool='sander', grip_verified=false`가 발행되고,
`safety_monitor`가 이를 **툴 낙하로 간주해 `FAULT_TOOL_DROP`을 래치**합니다
(`safety_monitor_node.py` `_on_tool_status`). 이후 모든 액션이 REJECT되며
`ResetSafety` 없이는 풀리지 않습니다. **`verify_grip`은 true로 두세요.**

### 1.6 ⚠️ v0.3에서 없어진 방어선 — 시작 전에 반드시 읽을 것 ★★

예전에는 **스캔이 손톱과 피부를 실측으로 구분**했고, 손이 격자 중심에서
3~4mm만 어긋나도 `E_COARSE_INSUFFICIENT` / `E_SEPARATION_LOW` 로 **공정이
시작조차 되지 않았습니다.** 그 노드가 없어졌습니다.

지금 손톱의 위치와 크기를 아는 유일한 근거는
`nail_bringup/config/static_frames.yaml` 에 **사람이 티칭해 넣은 숫자**이고,
**그 숫자가 틀렸는지 알려주는 코드는 어디에도 없습니다.** 틀린 자리를
그대로 갈고, 도포하고, UV를 쬡니다.

따라서 이 판의 테스트에서는:

1. **§6(티칭 확인)을 건너뛰지 마세요.** 다른 모든 공정 절의 전제조건입니다.
2. **더미/지그 위에서 먼저 하세요.** 사람 손은 전 공정이 한 번 이상
   무사히 돈 뒤에.
3. **경계를 실제보다 작게 잡으세요.** `nail_region.size_*` 를 실측보다
   1~2mm 작게 두는 편이 안전합니다 — 경계 밖은 곧 피부입니다.
4. **손 안착 지그가 흔들리면 티칭이 무효입니다.** 지그를 고정하고, 옮겼으면
   `nail_local_frame` 을 다시 티칭하세요.

## 3. `robot_skill_node` (NIS §5.1)

**띄우기**: `nodes:=safety,skill,tool` (그리퍼 확인에 tool_manager도 있으면 편함)

### 3.0 좌표가 어디서 오는지 (§3.2·§4 공통 배경)

설정 파일 3종의 역할:

| 파일 | 역할 | 읽는 노드 |
|---|---|---|
| `nail_skill/config/targets.yaml` | **이름 → 좌표** 주소록 | `robot_skill_node` |
| `nail_skill/config/tool_rack.yaml` | **툴 카탈로그** (위치이름 + 파지폭 + 툴길이) | `tool_manager` |
| `nail_bringup/config/static_frames.yaml` | **TF + 손톱 영역** (`nail_local_frame`, `nail_region`) | launch → 공정 노드 |

`PickPlace.target_key` 해석 순서 (`_target_task_pose`):

```
① targets.yaml 최상위 키에서 찾는다        ← 툴 5개가 여기 있음
② 없으면 그 이름을 TF 프레임으로 조회한다   ← 폴백 (stone_node 가 씀)
③ 둘 다 실패하면 E_INVALID_GOAL
```

현재 `targets.yaml` 키: `rack_transit`, `stone_tray`, `sander`, `brush`,
`coater`, `uv`, `tweezers`, 그리고 작업 시작 자세 `sander_work`,
`brush_work`, `coater_work`, `uv_work`.
`tool_rack.yaml`의 `slot_frame` 값이 이 키와 **글자 그대로 일치**해야 합니다.

```bash
# 지금 로드될 좌표 확인
cat install/nail_skill/share/nail_skill/config/targets.yaml
```

> **v0.3 삭제**: `probe`, `probe_work`(탐침), `stone_place`(스톤 부착 위치 —
> `static_frames.yaml` 의 `nail_local_frame` 으로 옮겨감).

### 3.1 `MoveTo` — `/skill/move_to`

```bash
ros2 action send_goal /skill/move_to nail_msgs/action/MoveTo "{
  target: {position: {x: 0.4, y: 0.0, z: 0.3},
           orientation: {x: 0.0, y: 1.0, z: 0.0, w: 0.0}},
  frame_id: 'base_link', linear: true,
  speed_ratio: 0.1, accel_ratio: 0.1, timeout_s: 15.0
}" --feedback
```

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 정상 이동 | 안전한 빈 공간 좌표 | `success=true`, `position_error_mm` < `move_pose_tolerance_mm`(기본 1.0) |
| 안전 차단 | E-Stop 누른 채로 goal 전송 | REJECT, `E_SAFETY_BLOCKED` |
| 타임아웃 | `timeout_s: 0.01`로 먼 좌표 | ABORT, `E_TIMEOUT` 또는 `E_MOTION_FAILED` |
| 도달 불가 | 작업영역 밖 좌표 | ABORT, `E_MOTION_FAILED` (`_verify_position_reached`가 걸러냄) |

**`MoveTo`를 먼저 쓰는 이유**: 새로 티칭한 좌표를 PickPlace로 바로 쓰기 전에,
`MoveTo(linear=true, speed_ratio: 0.05)`로 그 자리에 근접시켜 눈으로 확인하는
것이 안전합니다. **§6의 `nail_local_frame` 검증도 이 방법을 씁니다.**

### 3.2 `PickPlace` — `/skill/pick_place`

**실행 순서**:

```
PICK                                  PLACE
 ① approach(z + approach_height)로 이동  ① approach로 이동
 ② 그리퍼 개방                          ②  — (툴을 쥔 채)
 ③ target z로 하강                      ③ target z로 하강
 ④ expected_width_mm로 오므림            ④ 그리퍼 개방 → 툴 안착
 ⑤ approach로 복귀                      ⑤ approach로 복귀
```

`feedback.step`: 0=이동 1=하강 2=그립 3=검증 4=상승

**pick과 place의 목표 z는 동일합니다.** `target_key`의 `z_mm`은 "툴이 슬롯에
안착해 있을 때 그리퍼 높이" 하나로 정의되며, 꽂는 높이와 빼는 높이가 같아야
정상입니다.

#### 3.2.1 정상 픽 — 실제 티칭 좌표로

```bash
ros2 action send_goal /skill/pick_place nail_msgs/action/PickPlace "{
  mode: 'pick', target_key: 'sander', frame_id: 'base_link',
  approach_height_mm: 20.0, grip_width_mm: 50.0,
  expected_width_mm: 50.0, width_tolerance_mm: 1.0, verify_grip: true
}" --feedback
```

**육안 확인 순서** — 이 순서대로 안 보이면 그 단계가 실패한 것입니다:
1. 툴 위 20mm 지점으로 이동
2. **그리퍼가 활짝 열림** ← 안 열리면 §3.2.4로
3. 툴 손잡이 높이까지 하강
4. 그리퍼가 지정 폭으로 오므라들며 툴 파지
5. 다시 20mm 위로 상승

#### 3.2.2 정상 플레이스

```bash
ros2 action send_goal /skill/pick_place nail_msgs/action/PickPlace "{
  mode: 'place', target_key: 'sander', frame_id: 'base_link',
  approach_height_mm: 20.0
}" --feedback
```

툴이 슬롯 제자리에 안착해야 합니다. **툴이 슬롯 바닥을 누르거나 로봇이
버티는 느낌이 나면** 이동 중 툴이 그리퍼 안에서 미끄러진 것입니다:

```bash
ros2 param set /robot_skill_node place_clearance_mm 2.0
```

place할 때만 목표 z를 2mm 올려 툴을 살짝 떨어뜨립니다. 적용되면 로그에
`place_clearance_mm=2.0 적용 → z ... → ...mm`이 남습니다. 기본값은 0.0이라
설정하지 않으면 동작이 바뀌지 않습니다.

#### 3.2.3 판정표

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 정상 픽 | 위 §3.2.1 | `success=true`. **파지 여부는 육안 판정** (§1.5) |
| 정상 플레이스 | 위 §3.2.2 | `success=true`, 툴이 슬롯에 안착 |
| pick→place 왕복 | §3.2.1 직후 §3.2.2 | 툴이 원래 자리로 정확히 복귀 |
| 없는 키 | `target_key: 'probe'` (v0.3에서 삭제된 키) | ABORT, `E_INVALID_GOAL` — **로봇 안 움직임** |
| 빈 키 | `target_key: ''` | REJECT, `E_INVALID_GOAL` |
| 잘못된 mode | `mode: 'grab'` | REJECT, `E_INVALID_GOAL` |
| 안전 차단 | E-Stop 누른 채 | REJECT, `E_SAFETY_BLOCKED` |
| 취소 | 이동 중 `Ctrl-C` | `status: CANCELED` |

> "없는 키" 케이스에 일부러 `probe` 를 씁니다 — v0.3에서 정말 지워졌는지
> 확인하는 회귀 테스트를 겸합니다.

#### 3.2.4 그리퍼가 안 움직일 때 진단

```bash
ros2 service list | grep onrobot                # /onrobot/sendCommand 존재 확인
ros2 interface show onrobot_rg_msgs/srv/SetCommand
ros2 service call /onrobot/sendCommand onrobot_rg_msgs/srv/SetCommand "{command: 'o'}"     # 개방
ros2 service call /onrobot/sendCommand onrobot_rg_msgs/srv/SetCommand "{command: '120'}"   # 12.0mm
```

`dsr_adapter`가 보내는 것: 개방=`'o'`, 폭=`str(int(width_mm * 10))` (0.1mm 단위).

| 증상 | 원인 |
|---|---|
| 서비스가 목록에 없음 | 그리퍼 드라이버 미기동 |

| 서비스는 있는데 `'o'`도 무반응 | 명령 문자열 규약 불일치 — `SetCommand` 정의 확인 필요 |

## 4. `tool_manager` (NIS §5.2)

**띄우기**: `nodes:=safety,skill,tool` · 사전조건: §3.2 PickPlace 단독 테스트
통과 (ChangeTool은 그 위에 얹혀 있음)

### 4.0 무엇을 확인하는가

`tool_manager`는 **로봇을 직접 움직이지 않습니다.** `ChangeTool` goal을 받으면
`robot_skill_node`의 `/skill/pick_place`를 호출해 이동을 시킵니다.

```
ChangeTool('sander')
   │
   ├─ set_tcp('tcp_none')          ← 좌표 기준을 플랜지로 고정
   ├─ PickPlace(place, 현재 툴)     ← 반납. 툴이 없으면 건너뜀
   ├─ PickPlace(pick,  'sander')   ← 파지
   ├─ set_tcp('tcp_sander')        ← 공정 작업용 기준점으로 전환
   └─ /tool/status 발행
```

`feedback.step`: 0=반납 1=랙이동 2=픽업 3=TCP 4=검증

**`tcp_none`을 거치는 이유**: `targets.yaml`의 툴 좌표는 "그리퍼(플랜지)가
있어야 할 자리"로 티칭한 값입니다. 툴마다 `tcp_offset`이 다르면 직전에 들고
있던 툴에 따라 같은 좌표라도 실제 도달 높이가 달라집니다. 랙 이동 직전에
오프셋 0으로 되돌려 기준을 고정합니다.

### 4.1 기동 확인 (액션 보내기 전)

launch 로그에 아래가 보여야 합니다:

```
[tool_manager]: tcp_none 등록 완료 (랙 이동 기준 TCP)
[tool_manager]: TCP 동기화: tcp_sander = [0, 0, 0, 0, 0, 0]
[tool_manager]: tool_manager ready — tool_list=[...], rack_config 항목 5개 로드
```

> **v0.3**: `rack_config 항목 5개` 입니다 (probe 제외). **6개로 나오면**
> 옛 `tool_rack.yaml` 이 `install/` 에 남아 있는 것입니다 — 재빌드하세요.

`tcp_none 등록 실패`가 보이면 랙 도달 높이가 교체 순서에 따라 달라집니다 —
원인을 먼저 해소하세요.

> ⚠️ **`tcp_offset`이 전부 미실측입니다.** 5개 전부 `[0,0,0,0,0,0]` 입니다.
> 이 값은 기동 시 `add_tcp('tcp_<툴>')`로 컨트롤러에 등록되고, 교체 3단계의
> `set_tcp`가 **이후 모든 이동의 기준점을 여기로 바꿉니다** — §7 이후 공정
> 좌표가 툴 길이만큼 통째로 어긋납니다.
>
> 실측 전에는 TCP 등록을 건너뛰고 픽/플레이스만 확인하는 편이 안전합니다:
> ```bash
> ros2 launch nail_bringup test_bringup.launch.py sync_tcp_on_startup:=false
> ```
> (`tcp_none`은 이 설정과 무관하게 항상 등록되므로 랙 이동 기준은 유지됩니다.)
>
> `tcp_offset`에 넣을 값 = **플랜지 아랫면부터 툴 끝까지의 거리**
> (`[0, 0, 길이, 0, 0, 0]`). 티치펜던트 TASK 화면의 X/Y/Z/A/B/C(로봇 절대
> 자세)를 넣으면 안 됩니다.

### 4.2 정상 교체

```bash
ros2 action send_goal /tool/change nail_msgs/action/ChangeTool "{
  target_tool: 'sander', expected_width_mm: 0.0, width_tolerance_mm: 1.0,
  verify_after_grip: true, park_facing: 'into_rack'
}" --feedback

ros2 topic echo /tool/status --once
ros2 service call /tool/get_info nail_msgs/srv/GetToolInfo "{tool_id: ''}"
```

`expected_width_mm: 0.0`으로 두면 `tool_rack.yaml`의
`expected_grip_width_mm`이 쓰입니다 (권장 — 툴별 값이 한 곳에 모임).

### 4.3 판정표

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 정상 교체 | §4.2 | `state.current_tool='sander'`, `state.active_tcp='tcp_sander'`, `feedback.step`이 1→4 순서 발행, `/tool/status` 갱신 |
| 연속 교체 ★ | `sander` → `coater` → `sander` | 각 교체마다 반납(step 0)이 먼저 실행되고, **세 번 모두 같은 높이로 내려가는지 육안 확인** (tcp_none 검증) |
| 반납만 | `target_tool: 'none'` (툴 든 상태에서) | 랙 반납, `state.current_tool='none'` |
| 미등록 툴 | `target_tool: 'hammer'` | REJECT, `E_INVALID_GOAL` — **로봇 안 움직임** |
| **폐지된 툴** ★ | `target_tool: 'probe'` | REJECT, `E_INVALID_GOAL` — v0.3 회귀 테스트 |
| 안전 차단 | E-Stop 누른 채 | REJECT, `E_SAFETY_BLOCKED` |
| 취소 | 이동 중 `Ctrl-C` | `status: CANCELED`, 하위 PickPlace도 취소됨 |
| UV 반납 자세 ★ | `uv` 픽업 후 `'none'`으로 반납 | 반납 시 **광축이 랙 안쪽을 향하는지 육안 확인** (§10.0 통제 #6, UV 상시 ON이므로 필수) |

> 결과 필드는 `state.tool_id`가 아니라 **`state.current_tool`**입니다
> (`ToolState.msg`에 `tool_id` 필드는 없음).

> ⚠️ **"툴 미인식/파지 실패 → `E_GRIP_FAILED`" 케이스는 현재 재현되지
> 않습니다** (§1.5). 빈 슬롯을 지정해도 `success=true`가 나옵니다.
> 파지 실패는 육안으로만 판정하세요.

> ⚠️ **UV 반납 자세는 소프트웨어가 제어하지 않습니다.** `park_facing`
> 파라미터는 로그에만 남고 실제 자세에 반영되지 않습니다 —
> `targets.yaml`의 `uv` 좌표 자체가 "광축이 랙 안쪽"인 자세로 티칭되어
> 있어야 합니다. 노드가 기동 시 이 사실을 WARN으로 남깁니다.

## 5. `safety_monitor` ★★ (NIS §7)

**띄우기**: `nodes:=safety,skill,tool`

### 5.1 상태 발행

```bash
ros2 topic hz /safety/status        # publish_rate_hz(기본 5)와 일치하는지
ros2 topic echo /safety/status --once
```

> **v0.3**: 출력에 `scan_valid` 필드가 **없어야** 정상입니다. 남아 있으면
> `nail_msgs` 재빌드가 안 된 것입니다.

### 5.2 `ValidatePrecondition` — 스테이지별

```bash
ros2 service call /safety/validate nail_msgs/srv/ValidatePrecondition \
  "{stage: 'SAND', session_id: 'unit_test', required_tool: 'sander'}"
```

| stage | 필요 조건 (§7 표) | 테스트 |
|---|---|---|
| `SAND` | 안착 + sander 툴 + 더스트 컬렉터 ON | 컬렉터 OFF로 호출 → 더스트 사유 포함 |
| `BRUSH` | 안착 + brush 툴 | brush 미장착으로 호출 → 툴 사유 |
| `COAT` | 안착 + coater 툴 | 〃 |
| `CURE` | 안착 + uv 툴 | 〃 |
| `STONE` | 안착 + tweezers 툴 | 〃 |

**`blocking_reasons`는 항상 배열 전체를 확인하세요** — 막힌 이유가 여러 개일
때 하나만 주면 그 자체가 §7 규약 위반입니다.

> **v0.3 삭제**: `SCAN` · `INSPECT` 스테이지와 **모든 스테이지의 "스캔 valid"
> 조건**. `stage: 'SCAN'` 으로 호출하면 스테이지별 추가 검사 없이 공통 검사
> (safe_to_move, 안착, 툴 일치)만 돌아갑니다 — 별도 오류는 아니지만 의미가
> 없으니 쓰지 마세요.

### 5.3 E-Stop 처리 (물리 테스트, 필수)

1. 로봇 정지 상태 확인 후 **실제 E-Stop 버튼**을 누른다.
2. `ros2 topic echo /safety/status --once` → `safe_to_move=false`,
   `active_faults`에 `FAULT_ESTOP`, `estop_released=false` 확인.
3. 이 상태에서 아무 액션이나 `send_goal` → **REJECT** 확인
   (실행 중이던 액션이 있었다면 ABORT).
4. E-Stop 해제 → `ResetSafety` 호출 → `remaining_faults=[]`,
   `safe_to_move=true` 복귀 확인.

> **`auto_reset`이 `false`인지 반드시 확인**하세요
> (`ros2 param get /safety_monitor auto_reset`). `true`면 이 노드의 존재
> 의미가 사라진다고 NIS §7이 명시합니다 — 단위 테스트 항목 중 유일하게
> "값이 바뀌어 있으면 그 자체가 실패"인 파라미터입니다.

### 5.4 인터록 개별 확인

| 인터록 | 유발 방법 | 기대 |
|---|---|---|
| 안착 센서(`FAULT_NO_HANDREST`) | 손목/손 지그를 안착 센서에서 뗌 | `safe_to_move=false`, 재안착 시 자동 복귀(래치 아님) |
| 더스트 컬렉터(`FAULT_NO_DUST`) | 컬렉터 전원 OFF | SAND 스테이지 `ValidatePrecondition`이 `ok=false` |
| 통신 두절(`FAULT_COMM_LOST`) | 컨트롤러 네트워크 순간 분리 (팀과 상의 후) | `heartbeat_timeout_ms`(기본 1500ms) 경과 후 `comm_ok=false`, **래치됨** |
| 툴 낙하(`FAULT_TOOL_DROP`) | — | §1.5 참조. `grip_verified=false` 발행 시 래치되나, 정상 경로에서는 발생하지 않음 |

건너뛰지 마세요.** v0.2 에서 이 자리에 있던 `scan_node` 테스트를 대체합니다.

**띄우기**: `nodes:=frames,safety,skill,tool`
**준비물**: 손 안착 지그(고정된 상태), 자, 티치펜던트

### 6.1 지금 무엇이 로드돼 있는지 확인

```bash
# ① TF: 손톱이 어디 있다고 알고 있나
ros2 run tf2_ros tf2_echo base_link nail_local_frame

# ② 파라미터: 손톱이 얼마나 크다고 알고 있나
ros2 param get /sanding_node nail_size_x_mm
ros2 param get /sanding_node nail_size_y_mm
ros2 param get /sanding_node nail_boundary_points
```

①이 `Invalid frame ID "nail_local_frame"` 로 실패하면 **`frames` 토큰을
빠뜨린 것**입니다. ②는 launch 로그의
`[nail_bringup] 손톱 작업 영역: ... mm` 줄과 같은 값이어야 합니다.

### 6.2 티칭 절차 (실기 투입 전 1회, 지그를 옮길 때마다 반복)

1. 손(또는 더미)을 지그에 **실제 작업할 자세 그대로** 안착시킵니다.
2. 툴을 뺀 상태로, 티치펜던트를 TASK-BASE 좌표계로 두고 **그리퍼 끝을 손톱
   정중앙 표면에 살짝 닿게** 내립니다.
3. 화면의 X / Y / Z 세 숫자를 `nail_bringup/config/static_frames.yaml` 의
   `frames.nail_local_frame` 에 적습니다.
4. 손가락이 로봇 X축과 나란하지 않으면, 손톱 길이축(큐티클→손톱 끝)이 +X를
   향하도록 `yaw_deg` 를 채웁니다. **`roll_deg`/`pitch_deg` 는 0으로 두세요**
   — 툴을 아래로 향하게 만드는 자세 계산이 이 프레임이 수평이라는 전제 위에
   있습니다.
5. 자로 손톱의 **길이**(큐티클→끝)와 **폭**을 재서 `nail_region.size_x_mm` /
   `size_y_mm` 에 적습니다. **실측보다 1~2mm 작게 적으세요.**
6. 재빌드 + 재시작:
   ```bash
   colcon build --packages-select nail_bringup && source install/setup.bash
   ```

> 초기값(`x:325.55 y:-21.85 z:394.80`)은 예전 `targets.yaml` 의 `stone_place`
> (펜던트 실측)에서 옮겨온 **대체값**입니다. 플랜지 기준으로 읽은 값이고
> 손톱 정중앙이라는 보장이 없으니, 실기 투입 전 반드시 위 절차로 다시
> 티칭하세요.

### 6.3 검증 — 로봇으로 직접 확인 ★

**표면에 닿게 하지 말고, 표면 위 5mm 지점으로 보냅니다.**

```bash
ros2 action send_goal /skill/move_to nail_msgs/action/MoveTo "{
  target: {position: {x: 0.0, y: 0.0, z: 0.005},
           orientation: {x: 1.0, y: 0.0, z: 0.0, w: 0.0}},
  frame_id: 'nail_local_frame', linear: true,
  speed_ratio: 0.05, accel_ratio: 0.05, timeout_s: 20.0
}" --feedback
```

| 케이스 | 절차 | 기대 결과 |
|---|---|---|
| 원점 검증 ★★ | 위 명령 (`z: 0.005`) | **툴 끝이 손톱 정중앙 바로 위 5mm 에 온다.** 어긋나면 §6.2 로 돌아가 다시 티칭 |
| 표면 높이 검증 ★★ | `z: 0.0` 으로 아주 천천히 (`speed_ratio: 0.02`) | **손톱 표면에 막 닿는 높이.** 파고들면 z가 낮게 티칭된 것 — **손 대신 더미로 먼저 할 것** |
| 길이축 검증 | `{x: 0.006, y: 0.0, z: 0.005}` | 손톱 **끝(프리에지)** 쪽으로 6mm 이동. 옆으로 가면 `yaw_deg` 가 틀린 것 |
| 폭축 검증 | `{x: 0.0, y: 0.005, z: 0.005}` | 손톱 **옆** 으로 5mm 이동 |
| 경계 확인 | `{x: size_x/2000, y: 0.0, z: 0.005}` | 손톱 끝 **가장자리 안쪽**에 와야 함. 손톱 밖(피부 위)이면 `size_x_mm` 를 줄일 것 |
| TF 없음 | `frames` 토큰 빼고 실행 | ABORT — TF lookup 실패 (`E_MOTION_FAILED`) |

### 6.4 경계 파라미터 방어 확인

```bash
# 공정 노드를 하나 띄운 상태에서
ros2 param set /sanding_node nail_size_x_mm 0.0
ros2 action send_goal /process/sand nail_msgs/action/SandSurface "{session_id: 'unit_test'}"
```

**REJECT, `E_INVALID_GOAL`** 이 나야 합니다 (로그: `손톱 경계를 만들 수 없음`).
로봇이 움직이면 방어가 뚫린 것입니다. 확인 후 되돌리세요:

```bash
ros2 param set /sanding_node nail_size_x_mm 16.0
```

launch 단계 방어도 확인해 둡니다 — `static_frames.yaml` 의 `nail_region:`
블록을 잠깐 주석 처리하고 띄우면 **launch 자체가 실패**해야 합니다
(`nail_region 값이 유효하지 않다` 또는 `'nail_region:' 항목이 없다`).

>

## 12. `session_orchestrator` — 통합 스모크 테스트 (NIS §8)

개별 노드 단위 테스트가 모두 통과한 뒤에만 진행하세요. 이 노드는 로봇을 직접
움직이지 않고 위 노드들을 순서대로 호출만 합니다 — 여기서 나는 실패는 대부분
"개별 노드는 되는데 조합 순서/타임아웃이 안 맞는" 문제입니다.

**띄우기**: `nodes:=all` (`frames` 포함됨)

```bash
ros2 action send_goal /session/run nail_msgs/action/RunSession "{
  session_id: 'smoke_1', recipe_id: 'default',
  shape_profile_id: 'default', target_material: 'test_jig',
  layer_total: 1, enable_brush: true, enable_stone: false
}" --feedback
```

> **v0.3**: goal 에서 `max_rework` 가 삭제됐습니다. 결과에서도 `scan_result`,
> `all_results`, `total_rework` 가 사라졌습니다.

- `enable_stone: false`로 시작하세요.
- `target_material`에 사람 신체를 뜻하는 값이 들어가면 안전 검증에서 걸려야
  합니다(BR-029) — 정확한 검증 문자열은 orchestrator 구현 확인.
- 별도 터미널에서 `ros2 topic echo /process/status`를 같이 보면서 `stage`가
  **`PRECHECK → SAND → BRUSH → COAT → CURE → FINISH`** 로 넘어가는지 확인.
  **`SCAN`/`INSPECT`/`REWORK` 가 보이면 안 됩니다.**
- PRECHECK 가 요구하는 툴: `sander`, `coater`, `uv` (+brush, +tweezers).
  `probe` 를 요구하면 옛 빌드입니다.
- 툴 교체 순서 육안 확인: `sander → brush → coater → uv → none`
  (`layer_total: 1` 기준 5회).
- 취소: 중간에 `Ctrl-C` → 하위 액션 전부 cancel, 툴 반납(우선 UV), HOME 복귀
  (`abort_return_home` 기본 true).
- `enable_stone: true` 테스트 시: `tweezers` 교체 후 **`<툴>_work` 를 거치지
  않고** 바로 `PlaceStone` 이 `stone_tray` 로 PICK 하러 가는 것이 정상입니다
  (`targets.yaml` 에 `tweezers_work` 가 없음).

## 13. 완료 판정 체크리스트

각 노드 테스트를 "끝냈다"고 선언하기 전에:

- [ ] 정상 케이스 1개 이상 `success=true`로 통과
- [ ] 그 노드의 ★ 표시된 안전 관련 에러 케이스가 실제로 재현되고, 문서에 적힌
      이탈/후퇴 동작이 **육안으로** 확인됨
- [ ] `result.base.error.code`가 NIS §4 표준 코드와 정확히 일치
- [ ] 모든 ABORT 로그에 에러 코드 + 좌표/측정값이 있음 (`ros2 topic echo /rosout`)
- [ ] `/safety/status` 구독 반응(`safe_to_move=false` 시 REJECT/ABORT)을 최소 1회 확인
- [ ] 테스트 후 로봇을 HOME 또는 안전 위치로 복귀시키고, 장착 중이던 툴을 반납함
